## ログイン

管理者も講師も `/login` の**同じ入力欄**から入り、`Teacher.role` で行き先が変わる。

| role | 誰 | ログイン後 |
| --- | --- | --- |
| `ADMIN` | 社員 | `/`（管理者画面・PC） |
| `TEACHER` | 時間講師・学生講師 | `/t`（講師画面・スマホ） |

社員も授業を持つので、管理者は別テーブルにせず `Teacher` に役割を持たせている。

seed のログインは `sato` `suzuki`（管理者）、`takahashi` `tanaka` `ito` `watanabe` `yamamoto`
`nakamura`（講師）。**パスワードは全員 `juku-hr-demo-2026`。**

デモ用パスワードに `pass` や `password` のようなありふれた語を使わないこと。
ブラウザが既知の流出パスワード一覧と突き合わせていて、**「データ侵害で検出されました」と
警告を出してしまう**（`pass` は200万件超の流出で確認されている）。
デモ中にこれが出ると、アプリが侵害されたように見える。
変えるときは `npm run check:password` で流出していないことを確かめる。

打刻ページ `/p/[token]` だけはログイン不要。二次元コードのカードを配って、
教室の端末や講師のスマホで読む使い方のため。このトークンでできるのは打刻だけで、
給与明細などは見られない。

### 作り
依存を増やさず `node:crypto` だけで作っている。

- **パスワード** — scrypt。`"salt:hash"` の形で保存し、平文は持たない。
  照合は `timingSafeEqual`。ID が無い場合とパスワードが違う場合で、返す文言を変えない
  （分けると「このIDは存在する」と教えてしまう）
- **セッション** — 署名付き Cookie（`teacherId.期限.HMAC-SHA256`）。httpOnly。
  中身を書き換えると署名が合わず通らない
- **認可** — `lib/dal.ts` の `currentTeacher()`。React の `cache()` で包んでいるので
  1リクエストにつき DB は1回

`proxy.ts`（Next.js 16 で middleware から改名）は**Cookie の有無しか見ない**。
prefetch を含む全リクエストで走るため DB を引くと重く、署名も検証していないので防御にはならない。
公式ドキュメントも「proxy を認可の解決策にするな、DAL でやれ」としている。実際の判定は必ず DAL 側。

### proxy に「ログイン済みなら /login から追い出す」を書いてはいけない

proxy と DAL は見ているものが違う。proxy は Cookie の有無だけ、DAL は講師が実在し在籍中かまで見る。
そのため **proxy に「Cookie があれば /login → / へ」を入れると、リダイレクトループになる。**

```
/       → DAL: この講師はもう居ない → /login へ
/login  → proxy: Cookie があるから済み → / へ
/       → ... 無限ループ
```

これは開発中に DB を作り直したときだけでなく、**在籍中の講師を退職扱いにした瞬間にも起きる**。
そのため「本当にログイン済みか」の判断は DB を引ける `/login` のページ側で行っている。
`npm run verify:http` の [4][5] で、古い Cookie・退職者の Cookie でループしないことを確かめている。

**ここは試作の作り。** 実運用には、ログイン試行の回数制限、パスワードの初回変更の強制、
HTTPS の強制あたりが要る。

## 動かす

```bash
npm install
cp .env.example .env     # SESSION_SECRET を入れる（生成コマンドは .env.example に書いてある）
npx prisma migrate dev   # DB を作る（初回のみ）
npx prisma generate      # migrate では生成されないので必要
npm run seed             # 動作確認用のデータを入れる
npm run dev              # http://localhost:3000 → ログイン画面へ
```

| コマンド | 内容 |
| --- | --- |
| `npm run seed` | 講師8名・生徒30名・2か月ぶんのシフト・勤怠実績・連絡2件などを入れ直す |
| `npm run verify` | シフト／勤怠・給与／ログインと認可／欠席者カードを運用の流れどおりに検証する |
| `npm run verify:http` | dev サーバーを起動した状態で、ログイン前後の行き先とループしないことを検証する |
| `npm run check:password` | デモ用パスワードが既知の流出パスワードでないか照会する |
| `npm run db:reset` | DB を作り直して seed まで流す |
| `npm run db:studio` | Prisma Studio で中身を直接見る |

### 管理者画面と講師画面を並べて見る

同じホストの別タブでは Cookie を共有してしまうので、片方でログインするともう片方も同じ人になる。
**Cookie はホスト名で分かれる（ポート番号では分かれない）** ので、
ポートを変えても意味がない。ホスト名を変えて開く。

| 開くURL | 使う人 | seed のログイン |
| --- | --- | --- |
| http://admin.localhost:3000 | 管理者 | `sato` / `juku-hr-demo-2026` |
| http://teacher.localhost:3000 | 講師 | `takahashi` / `juku-hr-demo-2026` |

`*.localhost` はブラウザが 127.0.0.1 に解決するので、hosts ファイルの設定は要らない。
サーバーは1つのままでよい（`npm run dev` は1回だけ）。
`localhost:3000` と `127.0.0.1:3000` の組み合わせでも同じことができる。

セッション Cookie に `Domain` 属性を付けていないので、ホスト専用（host-only）になっている。
これが分かれる理由なので、`Domain` を付けないこと。

開発時はログイン画面にこの案内が出る（`app/login/page.tsx` の `DevHint`。本番では出ない）。

> **注意**: スキーマを変えたら `npx prisma generate` を実行し、**dev サーバーを再起動**すること。
> Prisma 7 の `migrate dev` はクライアントを生成しない。また起動中の dev サーバーは古いクライアントを
> 掴んだままなので、新しいモデルが `undefined` になる。SQLite のファイルも掴むので、
> `dev.db` を消したいときは先にサーバーを止める。

## 講師側の認可

**フォームから来た `teacherId` は信用しない。** 信用すると、開発者ツールで値を書き換えるだけで
他人のシフト・授業・給与を触れてしまう。講師側の Server Actions は必ず
`currentTeacher()`（`lib/dal.ts`）でセッションから引き直したものだけを使う。

- 授業は `canEditLesson()` で自分が担当したものだけ
- 連絡は `canReadMessage()` で自分が受信者のものだけ（一斉連絡は全員が受信者なので見える）
- 給与はセッションから引いた本人の id でしか計算しない

`npm run verify` の verify-teacher-access.ts で、講師が他の講師のものに触れないことを確かめている。

## ① シフト管理

### コマタイプ（レギュラー／夏期講習／冬期講習／春期講習）

シフト提出の画面には ComiruHR と同じくコマタイプのタブがある。ただのフィルタではなく、
**コマの時間帯そのものが期タイプごとに違う**ので分けている（`Period.termKind`）。

| コマタイプ | コマ | seed の期間 |
| --- | --- | --- |
| レギュラー | 3コマ 17:00〜21:20 | 4/6〜7/20、9/1〜12/22 |
| 夏期講習 | 6コマ 09:00〜18:50 | 7/21〜8/31 |
| 冬期講習 | 4コマ 09:00〜15:50 | 12/23〜1/7 |
| 春期講習 | 4コマ 10:00〜16:50 | 3/25〜4/5 |

レギュラーは学校の後なので夕方から、講習は学校が無いので朝から始まる。
`Period` の一意制約が `@@unique([termKind, name])` なのは、「夏期講習の1限」と
「レギュラーの1限」が別物だから。

**どの日がどのコマタイプかは日付から決まる**ので、講師には選ばせない（`termKindOfDate()`）。
タブで選んだタイプの期間外の日はカレンダー上で灰色になり、押しても入力できない。
タブを切り替えるとその期の最初の月へ飛ぶ（「夏期講習」を押したのに入力できる日が無い月が出ると戸惑うため）。
曜日の一括入力も、選んでいるタイプの期間内の日にしか入らない。

調整＆確定の盤面は週表示なので、1週間の中にレギュラーと講習が混ざることがある。
そのため列は日ごとにコマを引いて作っていて、日によって列数が変わる。

### 塾の予定（`SchoolEvent`）

管理者が `/calendar` で入れる休校日・行事。月表示と年間表示がある。
期間で持つので、1日の予定も「お盆休み 8/13〜8/16」のような連続した予定も同じ形。

**休校日（`kind=CLOSED`）はシフトを出せない。** 講師側のカレンダーで赤くなり「閉」が付き、
押しても入力できない。ただし画面で押せなくするのは見た目の話でしかないので、
`lib/shifts.ts` の書き込み側でも `isClosedDate()` で弾いている（曜日の一括入力も休校日を飛ばす）。
確定シフトの割当も同じ。**外すのは常に許す**（休校が後から決まったときに後始末できるように）。

行事（`kind=EVENT`）は印だけ。講師側のカレンダーに青い点が付き、日を選ぶと名前とメモが出る。

### 割当の公平さ

今までは「社員が講師の予定を前々から集めて手で組む」運用で、そこに**忖度や贔屓が入る**のと、
**講習期間に一部の講師へ負担が偏る**のが問題だった。そこで次の3点を軸にしている。

**希望は講師本人が入れた記録として残す**（`ShiftRequest`）。◎できれば入りたい／○出られる／×出られない。
×のコマに確定を入れると盤面が赤くなり、ダッシュボードにも警告が出る。

**割当を数字で見えるようにする**（`loadSummary`）。確定コマ数だけを見ると「たくさん希望を出した講師が
多く入って当然」なので、**充足率＝出られると答えたコマのうち実際に入った割合**も併せて出す。
`spread()` は希望を出した講師の中の割当コマ数の最大と最小の差で、偏りの目安。
シード直後はあえて偏らせてある（`seed.ts` の `favored` / `overlooked`）ので、
問題が画面で見えることを確かめられる。

**曜日でまとめて入れられる**。講師の予定はたいてい曜日で決まっているので、月カレンダーを1日ずつ押させない。

## ② 勤怠管理

`ShiftAssignment` が「予定」、`DutyRecord` が「実績」。当日の交代があるので別に持つ。
予定どおり出た日は勤怠管理の「予定どおりで実績にする」で一括転記できる。

- **Punch** — 1回の出勤〜退勤。1日に何本でも作れるので、1日複数回の出退勤に対応する
- **DutyRecord** — その日担当したコマ。コマ給の根拠
- **AdminWork** — 事務作業の分数。時給の根拠

打刻は**同じ操作で出勤／退勤が切り替わる**（出勤中なら退勤）。二次元コードを読むたびに呼ばれる想定なので、
講師に「出勤」「退勤」を選ばせない。二次元コードは `/attendance/qr` で印刷でき、
講師が自分のスマホで読むと `/p/[token]` が開く。読み込んだだけでは打刻せず、確認ボタンを1回押させている
（カードを見せ合ったときや戻るボタンでの誤打刻を防ぐため）。

## ③ 給与計算

`lib/payroll.ts` で勤怠実績から自動計算する。

```
支給合計 = コマ給 + 事務ぶん + 交通費
  コマ給   = Σ（授業形態ごとの担当コマ数 × その形態の単価）
  事務ぶん = 事務作業の合計時間 × 時給
  交通費   = 出勤日ごとに支給
```

### コマ給は授業形態ごと（`WageRate`）

同じ講師でも、集団を持つ日と個別を持つ日で単価が変わる（PDF の事例
「同じ講師でも指導内容で時給が変わる」に対応）。単価は `/payroll/settings` で設定する。

| 形態 | 定数 |
| --- | --- |
| 集団 | `GROUP` |
| 個別 1対1 | `INDIV_1` |
| 個別 1対2 | `INDIV_2` |

このため **`DutyRecord` は「どの形態を担当したか」まで持つ**。コマ数だけでは金額が出せない。
勤怠管理のコマのボタンは、押すたびに 未担当 → 集団 → 1対1 → 1対2 → 未担当 と回る。
確定シフトを実績に写すときは、時間割（`Lesson`）があればその形態を引き継ぐ
（個別は受講人数で 1対1 / 1対2 を分ける）。

**単価が未設定の形態は 0 円にせず `rate: null` にして警告を出す。** 黙って0円で計算すると、
設定漏れが「その講師は働いていない」ように見えて気づけない。給与計算の画面に赤い警告が出る。
seed では山本さんに集団の単価を入れていないので、この警告が実際に出る。

**交通費は期（`Term`）で単価が変わる。** 通常期は定期券があるので `commuteRegular`（多くの塾では0円）、
講習期間は定期券が無い前提で `commuteSpot`。判定は `usesSpotCommute()` で `Term.kind` を見る。

シード直後の7月（〜7/20はレギュラー期間）は交通費が0円になるが、これはバグではなく
全員が定期券を持っている前提だから。夏期講習（7/21〜）の日を勤怠管理で実績にすると単価が切り替わる。

端数は**月合計の分数から1回だけ**計算する。1件ずつ丸めると誤差が積もるため。
出勤日は「打刻がある日」と「コマを担当した日」の和集合（打刻し忘れても拾う）。

## ④ 講師連絡

宛先を選ばずに送ると全員宛て（一斉連絡）、選べば個別連絡。`kind=SURVEY` にして選択肢を1行1つ書くと
アンケートになり、詳細画面で集計が出る。既読は**講師が講師画面で開いた時点**で付く
（「既読にする」ボタンを押させない）。管理者画面からも手で切り替えられる。

## 欠席者カード

紙の運用は「欠席者ごとに1枚、手で書く」だった。これを分解している。

- **授業で進んだ内容と宿題は、その授業の欠席者全員に共通** → `LessonRecord` に**1回だけ**書く
- **生徒ごとに違うのはひとことコメントだけ** → `AbsenceCard.comment`
- 出欠で「欠席」を選んだ時点でカードは**自動生成**され、授業記録の内容が写る

個別指導では生徒ごとに内容が違うのでカード側で上書きでき、渡した後のカードは「渡した紙の控え」なので
授業記録を直しても変わってはいけない。そのため `AbsenceCard` は `LessonRecord` を参照せず**複製して持つ**。
追従させるかは「カードの内容が直す前の授業記録と同じままか（＝手を入れていないか）」で決める。

## これから作る

**「いつ開講するか」を決める工程**。ここが本命。いまは最後の「誰を入れるか」だけが自動で、
その前の工程は手作業のまま。3段階に分けている。

| 段階 | 内容 | 状態 |
| --- | --- | --- |
| A | 量（週コマ数）と配置を持てるようにし、必要人数を計算で出す | **済** |
| B | クラスや生徒を選ぶと、担当できる講師が出られる枠を色で見せる（決めるのは人） | 未 |
| C | 配置そのものを自動化する。個別は詰めると人件費が直接下がる（1対1×4回 → 1対4×1回） | 未 |

C まで行くと制約付き最適化になる。考慮したいのは講師の科目適性（`TeacherSubject.level` を用意済み）、
**生徒が同じ時間に2つの授業に出られないこと**、個別ブースが騒がしくならないこと。

**生徒の相性と騒音を表すモデルはまだ無い。** これは毎晩22時ごろの10分程度のミーティングで
口頭で共有されている暗黙知で、フォームに書かせる形にすると埋まらない。
メモから候補を拾う試作は `lib/ai/` にある（Ollama・MVP 外）。

## 決めごと

- **日付は `"YYYY-MM-DD"` の文字列**で持つ。タイムゾーン起因の1日ずれを避けるため。
  文字列のまま範囲比較・ソートができるので、期間の判定も素直に書ける。時刻も `"HH:MM"` の文字列。
- **SQLite は enum 非対応**なので、区分値は `String` + `lib/constants.ts` の定数で表現する。
- Prisma 7 はドライバアダプタが必須。SQLite は `@prisma/adapter-better-sqlite3` を使う。
  設定は `prisma.config.ts`（`package.json` の `prisma` キーではない）。
