## 3. ライセンスの意味と、やるべきこと

### 許可取りは要らない

MIT・Apache-2.0・BSD はいずれも**「誰でも自由に使ってよい」**というライセンス。
**開発元に連絡したり、申請したり、承認をもらったりする必要はない。**
塾で業務利用しても、お金を取って売っても、条件を満たせば問題ない。

### 唯一の義務：著作権表示を残す

| ライセンス | 義務 |
| --- | --- |
| MIT | 著作権表示とライセンス文を残す |
| BSD-2-Clause | 同上 |
| Apache-2.0 | 同上＋改変した場合はその旨を書く（特許条項もあるが利用者側の不利益はない） |

**Webアプリの場合、この義務はほぼ自動的に満たされる。**
ライブラリのソースコードそのものを配布するわけではなく、
`node_modules` の中のライセンスファイルを消さなければよい。

念のため、**画面のどこかに「使用しているオープンソースソフトウェア」の一覧を置いておくと確実。**
（工数0.5人日。必須ではないが、納品物としては丁寧）

### 注意すべきライセンス（今は使っていない）

もし今後これらのライセンスのライブラリを入れる場合は、**PMに相談してから**にする。

| ライセンス | 何が問題か |
| --- | --- |
| **GPL / AGPL** | 自分のコードもソース公開を求められる場合がある。**AGPL はWebサービスでも公開義務が発生する** |
| **SSPL** | 商用SaaSでの利用に強い制限 |
| **BUSL（Business Source License）** | 一定期間、商用利用が制限される |
| **独自ライセンス** | 中身を読まないと判断できない |

## 4. これから使いたくなるライブラリ（ここが本番）

**このアプリはカレンダーと表が主役**なので、開発中に必ず「専用ライブラリを使いたい」という話が出る。
その多くが**有料**であり、しかも**開発者1人あたりの年額課金**である。

### 4-1. カレンダー／スケジューラ ← 最も危険

| ライブラリ | 無料の範囲 | 有料になる条件 | 金額 |
| --- | --- | --- | --- |
| **FullCalendar 標準** | MIT。**無料** | — | 0円 |
| **FullCalendar Premium** | 非商用のみ無料 | **営利企業が使う場合は商用ライセンスが必須** | **$480**（約7.5万円） |

**なぜ危険か** — シフトの盤面は「縦に講師、横に時間」という**リソースタイムライン表示**であり、
これはまさに FullCalendar Premium の機能である。**「盤面を作るのに便利そう」で入れると有料になる。**

判定は**塾が営利事業かどうか**で決まる。開発者が学生でも、**塾が business として使えば商用**
（[FullCalendar 商用ライセンス](https://fullcalendar.io/license)）。
Vercel の無料プランと同じ構図なので注意。

**回避策：使わない。** 試作品はこの盤面を**HTMLの表 + Tailwind だけで既に作っている**

## 4-7. 他社に販売する場合（2026-08-10 追記）

**塾に売り込む前提が加わったため、自社利用のときとは別の条件が効いてくる。**

### 費用は0円のまま

本番に載る依存パッケージ **179個（推移的な依存を含む）**を実際に洗った結果。

| ライセンス | 件数 |
| --- | --- |
| MIT | 125 |
| Apache-2.0 | 23 |
| ISC | 20 |
| BSD-3 / BSD-2 / 0BSD | 6 |
| その他（Unlicense・デュアルライセンス等） | 5 |

**GPL・AGPL・SSPL・BUSL は0件。** いずれも商用販売と再配布を無条件で認めるライセンスなので、
**何校に売ってもライセンス費用は増えない。**

### 増える義務は「著作権表示」だけ

MIT も Apache-2.0 も条件はこれに尽きる。ただし**自社利用のときより重くなる。**

| 提供の形 | 義務 |
| --- | --- |
| 自社サーバーで動かし、画面だけ提供（SaaS） | 再配布にあたらないため実質不要 |
| **塾のサーバーに納品** | **使用OSS一覧の同梱が必要**（工数0.5人日） |

Apache-2.0（Prisma など23件）は、**改変した場合その旨を明記**する義務も加わる。

### 有料ライブラリは「開発者ライセンス」では足りない

**ここが自社利用との最大の違い。**
FullCalendar Premium の $480/開発者/年 は自社で使う場合の価格であり、
**作ったものを顧客に納品・販売する形は OEM ライセンス（価格非公開・個別見積）**にあたる。
AG Grid や MUI X も同種の区別を設けている。

> **売る前提では、有料ライブラリの検討は「年◯万円」ではなく「見積を取るところから」になる。**

### 調査中に見つけたもの

- **`seq-queue`** … `package.json` にライセンス欄が無く、機械的な一覧では「記載なし」に出る。
  同梱の `LICENSE` は **MIT**（書き忘れ）。来歴は `prisma → mysql2 → seq-queue` で、
  このアプリは SQLite しか使わないため実際には動かない。監査で指摘されたとき用の記録
- **`caniuse-lite`** … CC-BY-4.0 だが Next のビルド時データ。成果物には載らない

## 5. 追加する前のチェックリスト

新しいライブラリを入れるときは、**PMに相談する前に自分でこれを確認する。**

1. **`package.json` の `license` フィールドを見る** — MIT / Apache-2.0 / BSD / ISC なら基本的に問題なし
2. **「Pro」「Premium」「Enterprise」という名前の版が無いか探す** — あれば無料版の機能制限を確認
3. **公式サイトに Pricing ページがあるか見る** — あれば有料版が存在するということ
4. **「非商用は無料」と書いていないか探す** — 塾で使う時点で商用にあたる
5. **開発者ごとの課金か確認する** — 人数が増えると費用が増える

### インストール済みのライセンスをまとめて確認するコマンド

```powershell
# juku_HR ディレクトリで実行
npx license-checker --summary
```

**リリース前に1回、これを実行して GPL / AGPL / SSPL が混ざっていないことを確認する。**
（工数0.5人日）

## 7. PM に確認すること

| # | 決めること | 影響 |
| --- | --- | --- |
| 1 | **有料ライブラリの導入を禁止するか** | 禁止すれば、ライブラリ費用は構造的に0円で固定される |
| 2 | 依存パッケージの追加に承認を要るようにするか | 意図しない課金・ライセンス事故を防げる |
| 3 | リリース前のライセンス確認を完了条件に入れるか | 工数0.5人日 |
| 4 | 使用OSSの一覧を画面に出すか | 工数0.5人日。必須ではないが納品物として丁寧 |

**推奨：#1 を「原則禁止・必要なら PM 承認」にする。**
今の作りで足りているので、実質的な制約にならないうえ、費用の上限が確定する。
