# 7. シフト自動化 要件

本章は「7. シフト自動化」のみを対象とする。路線自動化は別担当のため本章では扱わない。
第1〜5章・第9章（システム全体要件・共通データ・チーム共通ルール）は前提として引き継ぐ。

---

## 7.0 前提

### 7.0.1 土台にする試作品

リポジトリには試作品が2つある。**シフト自動化は `juku_HR` を土台にする。**

| | `juku-app`（LuBo School） | `juku_HR`（塾HR） |
| --- | --- | --- |
| 対象ユーザー | 生徒・保護者・講師・管理者 | 講師・管理者 |
| シフト機能 | **未着手**（README「今後の実装予定 フェーズ3」） | 希望収集・手動割当・偏りの可視化が実装済み |
| データ保存 | `data/data.json`（JSON 全読み書き） | Prisma + SQLite（期間検索・集計が可能） |
| 期（レギュラー／講習）の概念 | 無し | 有り（`Term` / `Period.termKind`） |
| 休校日 | 無し | 有り（`SchoolEvent`） |
| 割当の公平性指標 | 無し | 有り（`loadSummary` / `spread`） |

**採用理由** — シフト自動化は「講師 × 日 × コマ」の集合に対する制約付き割当であり、
期間指定の絞り込みと集計が必須になる。`juku-app` の JSON 全読み書きではこれが成立しない。
また `juku_HR` には自動化の入力になる希望データ（`ShiftRequest`）と、
出力の妥当性を測る指標（充足率・偏り）が既にあるため、追加すべきものが明確である。

**`juku-app` の扱い** — 統合はしない。将来「確定シフトを生徒・保護者に見せる」段階で
連携先の候補になるが、本章の範囲外とする（→ 7.7 未決定事項）。

### 7.0.2 試作品に既にあるもの／無いもの

自動化を実装するにあたり、以下を出発点とする。

**既にあるもの（流用する。作り直さない）**

| 資産 | 場所 | 内容 |
| --- | --- | --- |
| 希望データ | `ShiftRequest` | 講師 × 日 × コマ、`OK` / `PREFER` / `NG` |
| 確定データ | `ShiftAssignment` | 講師 × 日 × コマ |
| コマ定義 | `Period` | 期タイプごとに時間帯が違う（`@@unique([termKind, name])`） |
| 期 | `Term` | レギュラー／夏期／冬期／春期。日付から期タイプが決まる（`termKindOfDate`） |
| 休校日・行事 | `SchoolEvent` | `kind=CLOSED` の日は希望も割当も不可 |
| 偏りの集計 | `lib/shifts.ts` `loadSummary()` / `spread()` | 充足率・最大最小差 |
| 講師側の提出画面 | `/t` | 月カレンダー・曜日一括入力 |
| 管理者側の盤面 | `/shifts/board` | 週表示・手動で確定／解除 |
| 認可 | `lib/dal.ts` | `currentTeacher()` / `requireAdmin()` |
| **講師の担当科目** | `TeacherSubject` | 科目 + `level`（1=可 / 2=得意 / 3=専門）。**未使用のまま用意されている** |
| **科目** | `Subject` | 名称・表示順 |
| **教室・ブース** | `Room` | `format`（集団/個別）・`capacity`（収容人数） |
| **時間割の入れ物** | `Lesson` | 日 × コマ × 科目 × 講師 × 教室。**段階3の出力先がそのまま存在する** |
| **生徒の配置** | `Attendance` | 授業 × 生徒。段階3で生徒を置く先 |
| 生徒 | `Student` | 学年・在籍状況 |

`TeacherSubject` は「時間割自動作成で使う科目適性」というコメント付きで既に定義されており、
`Lesson` / `Attendance` も揃っている。**時間割のデータ構造は試作品に既にある。無いのは作る処理だけ。**

**無いもの（本章で新規に作る）**

| 不足 | なぜ自動化に必須か |
| --- | --- |
| **生徒の受講予定** | 「誰がいつ何の科目を受けに来るか」が無いと、必要な科目と人数が決まらない。段階1の入力そのもの |
| **需要（科目別の必要講師数）** | 現状は人が盤面を見て割り当てるため需要が暗黙。「英語2人・数学1人」の形で持つ必要がある |
| **講師ごとの勤務上限** | 1日・週の上限コマ数、連続コマ上限が無いと、公平性だけを見て1人に詰め込む解が出る |
| **確定状態（下書き／確定）** | 全体要件「確定前と確定後を区別する」に対応する状態が `ShiftAssignment` に無い |
| **変更履歴** | 全体要件「変更履歴」に対応するテーブルが無い |
| **出勤シフトの自動割当エンジン** | 段階2の中核。現状は手動トグルのみ |
| **時間割の自動作成エンジン** | 段階3の中核。`Lesson` を作る処理が無い（試作品 README の「これから作る」） |
| **未回答の扱い・提出締切** | 「回答が無い＝出られる」なのか不明。自動化では明示が必要 |
| **同席させない組み合わせ** | 生徒の相性・騒音が口頭の暗黙知のまま。段階3で最低限これだけは持つ必要がある |

### 7.0.3 本章の範囲

**シフトと時間割は分けられない。** 本章は両方を1つの流れとして扱う。

分けられない理由は、必要人数の性質にある。

- あるコマに必要なのは「講師4人」ではなく「**英語2人・数学1人・国語1人**」である。
  科目を見ずに人数だけ合わせると、**時間割が組めないシフトが「正しいシフト」として確定してしまう**
- その科目が何コマ必要かは、**生徒の受講予定**から決まる。生徒が来ない科目にコマは要らない

したがって、シフトを決める要素は次の3つになる。

1. **生徒の予定** — いつ、誰が、何の科目を受けに来るか
2. **講師の入れる日時** — シフト希望
3. **講師の教科** — 誰が何を教えられるか

### 3つの段階

これらを1つの流れとして、3段階に分けて自動化する。

| 段階 | 内容 | 入力 → 出力 |
| --- | --- | --- |
| **段階1** | **需要の算出** | 生徒の受講予定 → 日 × コマ × 科目 × 形態 ごとの必要講師数 |
| **段階2** | **出勤シフトの作成** | 需要 + 講師の希望 + 講師の担当科目 → 誰がいつ出勤し、何を担当するか |
| **段階3** | **時間割の作成** | 出勤シフト + 生徒の受講予定 → 誰がどの生徒を、どの教室・ブースで見るか |

### なぜ1つの最適化問題にしないのか

3つをまとめて「生徒 × 講師 × 教室 × 科目 × コマ」の一括最適化として解く方法もあるが、採らない。

- **確定のタイミングが違う。** 出勤シフトは早く確定しないと講師が予定を立てられず、給与にも直結する。
  一方、生徒の配置は当日の欠席・振替で動く。同じ確定単位にできない
- **説明できなくなる。** 一括最適化は「なぜこの人がこの日なのか」を現場に説明できない。
  忖度・贔屓への対策として始めた機能が、別のブラックボックスに置き換わっては意味がない
- **段階2まででも業務は回る。** 段階3が未完成でも、出勤シフトさえ出れば現場は動ける。
  段階的にリリースできる

### 段階を分けるうえでの絶対条件

**段階2の出力は、段階3が成立することを保証しなければならない。**
「シフトは埋まったが時間割が組めない」を許すと、分けた意味がなくなる。
そのため次の2つを必須とする。

- 段階2のハード制約に **科目の充足**（H12）を含める
- 段階2の確定前に、**段階3を試作して成立するか検証する**（→ FR-C12「時間割成立チェック」）

段階3で組めなかった場合は、理由を添えて段階2へ差し戻す。

### 含まないもの

| | 内容 |
| --- | --- |
| 含まない | 給与計算・勤怠打刻（既存機能。確定シフトを受け取って動く。本章では変更しない） |
| 含まない | 生徒の相性・騒音を完全に考慮した最終的な席割り（→ 7.5.6 で「同席させない組み合わせ」の登録までを扱い、残りは手動調整とする） |

**校舎について** — v1 は**単一校舎**を前提とする。複数校舎（講師の校舎間移動を含む）は
拡張点として 7.7 に記載する。ただしデータモデルは後から校舎を足せる形にしておく（→ 7.5.7）。

## 7.1 機能概要

生徒の受講予定・講師のシフト希望・講師の担当科目の3つをもとに、
**指定した期間の出勤シフトと時間割を自動で作成する**機能。

作成した案は下書きとして保存され、管理者が盤面上で確認・手修正したうえで確定する。
確定した内容だけが講師に公開される。

処理は段階1（需要の算出）→ 段階2（出勤シフト）→ 段階3（時間割）の順に進む。
段階2で確定するのは「誰がいつ出勤し、何の科目を担当するか」まで。
段階3の「誰がどの生徒を見るか」は、当日の欠席・振替で動くため確定単位を分ける（→ 7.0.3）。

### 7.1.1 解決する課題（第3章との対応）

| 課題 | 本機能での解決 |
| --- | --- |
| 情報が紙・Excel・チャットに分散 | 生徒の受講予定と講師の希望を、それぞれ本人・担当者の入力として一元化 |
| 情報収集や入力に時間がかかる | 提出状況を一覧表示。未提出者を特定できる |
| 担当者の経験や記憶に依存 | 「この科目はこの先生」という頭の中の対応を `TeacherSubject` として明示し、割当ルールを重み付きの評価式として明文化（→ 7.5.5） |
| 条件の見落とし・入力ミス | ハード制約（→ 7.4）を機械的に検証。違反は保存させない |
| 作成後の修正や共有に時間がかかる | 確定と同時に講師側画面へ反映 |

さらに `juku_HR` の運用課題として挙がっている以下にも対応する。

- **忖度・贔屓が入る** → 割当根拠を数値として残し、盤面に表示する
- **講習期間に一部の講師へ負担が偏る** → 充足率の均等化を評価式の主項目に置く
- **時間割が組めないシフトができてしまう** → 科目の充足をハード制約にし（H12）、確定前に時間割の成立を検証する

### 7.1.2 業務フロー

```
【段階1】需要の算出
[管理者] 対象期間・締切を決めてシフト計画を作成
              ↓
[管理者] 生徒の受講予定を登録（曜日パターン → 日別に上書き）
              ↓
   システム  日 × コマ × 科目 × 形態ごとの必要講師数を自動算出
              ↓
[管理者] 算出結果を確認・上書き（模試の日に増やす等）

【段階2】出勤シフトの作成
[講師]   締切までにシフト希望を提出（既存の /t 画面）
              ↓
[管理者] 提出状況を確認 → 未提出者へ督促 or 代理入力
              ↓
[管理者] 「シフト自動作成」を実行
              ↓
[管理者] 盤面で結果を確認・手修正・ロック → 必要なら再実行
              ↓
   システム  時間割が成立するか検証（→ FR-C12）
              ↓                    ↓ 成立しない
[管理者] シフトを確定          理由を出して段階2へ差し戻し
              ↓
[講師]   自分の確定シフトを閲覧（既存の /t 画面に反映）

【段階3】時間割の作成
[管理者] 「時間割自動作成」を実行
              ↓
   システム  出勤講師に生徒を割り当て、教室・ブースを決める
              ↓
[管理者] 配置を確認・手修正（相性・騒音の最終調整はここで人が行う）
              ↓
[管理者] 時間割を確定 → 講師の画面に自分の担当が出る
```

段階1と段階2の間、段階2と段階3の間はそれぞれ独立して実行・再実行できる。
生徒が増えて需要が変わったときは段階1から、講師の都合が変わったときは段階2からやり直す。

## 7.2 入力情報

自動作成の実行時に読み込むデータ。すべて既存または新規のテーブルから取得し、
実行時に人が入力する項目は 7.2.5 のパラメータのみとする。

### 7.2.1 対象範囲を決める入力

| 項目 | 取得元 | 形式 | 必須 | 備考 |
| --- | --- | --- | --- | --- |
| 対象開始日 | `ShiftPlan.fromDate` | `"YYYY-MM-DD"` | ○ | |
| 対象終了日 | `ShiftPlan.toDate` | `"YYYY-MM-DD"` | ○ | 開始日以上であること |
| 休校日 | `SchoolEvent` (`kind=CLOSED`) | 期間 | — | 該当日は対象から除外 |
| 期 | `Term` | 期間 + `kind` | — | 日付から期タイプを決める |
| コマ定義 | `Period` | `termKind` / `startTime` / `endTime` / `order` | ○ | 対象期タイプのコマが1件も無ければ実行不可 |

### 7.2.2 生徒側の入力（段階1：需要の算出に使う）

| 項目 | 取得元 | 形式 | 必須 | 備考 |
| --- | --- | --- | --- | --- |
| 生徒 | `Student` (`active=true`) | 学年 | ○ | 退塾者は対象外 |
| **受講予定** | `StudentSchedule`（新規） | 生徒 × 曜日 or 日 × コマ × 科目 × 形態 | ○ | 「田中さんは毎週火曜2限に英語（1対2）」 |
| 科目 | `Subject` | | ○ | 既存 |
| 教室・ブース | `Room` | `format` / `capacity` | ○ | 既存。段階1では収容可能数の上限確認に使う |

**受講予定は曜日パターンで持ち、日別に上書きできる**。ほとんどの生徒は「毎週◯曜」で通うため、
1日ずつ入力させない（講師のシフト希望と同じ考え方）。振替・体験・季節講習の単発受講は日別で入れる。

### 7.2.3 講師側の入力（段階2：出勤シフトの作成に使う）

| 項目 | 取得元 | 形式 | 必須 | 備考 |
| --- | --- | --- | --- | --- |
| 講師 | `Teacher` (`active=true`) | | ○ | 退職者（`active=false`）は対象外 |
| 雇用区分 | `Teacher.employment` | `FULL_TIME` / `PART_TIME` / `STUDENT` | ○ | 最低出勤条件の判定に使う |
| シフト希望 | `ShiftRequest` | `OK` / `PREFER` / `NG` | ○ | レコード無し＝未回答 |
| **担当科目** | `TeacherSubject` | 科目 + `level`（1=可 / 2=得意 / 3=専門） | ○ | **既存だが未使用。ここで初めて使う** |
| 必要講師数 | `ShiftDemand`（新規） | 日 × コマ × **科目** × **形態** × 人数 | ○ | 段階1の出力。0 のコマは授業を開かない扱い |
| 勤務上限 | `TeacherShiftRule`（新規） | 1日/週の上限コマ数・連続上限・週の下限 | — | 未設定なら既定値（→ 7.5.7） |
| ロック済み割当 | `ShiftAssignment.locked=true` | | — | 自動作成でも動かさない |

**担当科目の登録が必須になる。** 全講師について `TeacherSubject` が1件も無い状態では、
科目別の需要を満たせないため自動作成を実行できない（→ P8）。
`level` は「教えられる／得意／専門」の3段階で、割当の優先度に使う。

### 7.2.4 段階3（時間割の作成）で追加で使う入力

| 項目 | 取得元 | 形式 | 必須 | 備考 |
| --- | --- | --- | --- | --- |
| 確定した出勤シフト | `ShiftAssignment` | 講師 × 日 × コマ × 科目 | ○ | 段階2の出力 |
| 受講予定 | `StudentSchedule` | | ○ | 誰を置くか |
| 教室・ブース | `Room` | `format` / `capacity` | ○ | 個別ブースは `capacity=2` など |
| **同席させない組み合わせ** | `StudentConflict`（新規） | 生徒 × 生徒 | — | 相性・騒音の暗黙知のうち、登録できる部分だけを持つ |

### 7.2.5 実行時パラメータ

| 項目 | 型 | 既定値 | 説明 |
| --- | --- | --- | --- |
| `mode` | `FULL` / `FILL` | `FULL` | `FULL`＝ロック以外を破棄して作り直す。`FILL`＝既存の割当を残し、未充足のコマだけ埋める |
| `weights` | 重みの組 | 7.5.5 の既定値 | 公平性・希望尊重などの重み。画面から変更できる |
| `respectPrevious` | boolean | `true` | 直前月の充足率を初期値に加味し、期をまたいだ偏りを是正する |

**未回答の扱い（重要）** — 未回答（`ShiftRequest` のレコードが無い）のコマには
**割り当てない**。「出られると答えていないコマに入れられていた」という事故を避けるため、
沈黙を承諾として扱わない。未提出の講師は自動作成の候補から外れ、警告に出る（→ 7.3.3）。

## 7.3 出力情報

### 7.3.1 需要（段階1の出力）

`ShiftDemand` のレコード群。1件が「この日のこのコマに、この科目・この形態の講師が何人要るか」を表す。

| 項目 | 内容 |
| --- | --- |
| `date` / `periodId` | いつ |
| `subjectId` | 何の科目か |
| `format` | 集団 / 個別1対1 / 個別1対2 |
| `required` | 必要な講師数 |
| `studentCount` | 根拠になった生徒数。「なぜ2人必要なのか」を示す |

**算出結果は管理者が上書きできる。** 生徒の受講予定に無い事情（模試の監督、体験授業の対応枠）
があるため、自動算出はあくまで下敷きとして扱う。

### 7.3.2 シフト案（段階2の出力）

`ShiftAssignment` のレコード群。
1件が「この講師は、この日のこのコマに出勤し、この科目を担当する」を表す。

| 項目 | 内容 |
| --- | --- |
| `teacherId` / `date` / `periodId` | 誰が・いつ・どのコマか |
| `subjectId` | **担当する科目**（どの需要を埋めたか） |
| `format` | 集団 / 個別1対1 / 個別1対2。給与のコマ給単価に直結する |
| `planId` | どの計画で作られたか |
| `source` | `AUTO`（自動作成）/ `MANUAL`（手修正） |
| `locked` | 再実行時に保護するか |
| `score` | 割当時の評価値。なぜこの人になったかの根拠として保持する |

### 7.3.3 時間割（段階3の出力）

**既存の `Lesson` と `Attendance` にそのまま書き込む。新しい入れ物は作らない。**

| 項目 | 内容 |
| --- | --- |
| `Lesson` | 日 × コマ × 科目 × 講師 × 教室（ブース）。1件が1つの授業枠 |
| `Attendance` | その授業枠に置かれた生徒。初期状態は `PRESENT` |

`Lesson` が既存モデルであることには実利がある。**授業記録・欠席者カード・出欠管理が
そのまま動く**（試作品で既に実装済み）。段階3を作れば、下流の機能が自動で繋がる。

### 7.3.4 作成結果サマリ

自動作成の実行直後に画面へ返す。保存もする（`ShiftPlan.lastResult`）。

**段階2（出勤シフト）**

**段階3（時間割）**

| 項目 | 内容 |
| --- | --- |

| 未配置の生徒一覧 | 生徒・日・コマ・科目・理由（→ 7.3.5） |

### 7.3.5 警告・未割当の理由

「エラーや未割り当てを確認できる」（第10章 優先度6）に対応する。
未充足には**必ず理由を1つ以上付ける**。理由の無い未充足は出さない。

**段階2：シフトが埋まらない理由**

| 理由コード | 表示 | 判定 |
| --- | --- | --- |
| `NO_CANDIDATE` | 出られると答えた講師がいない | そのコマの `OK`/`PREFER` が 0 件 |
| **`NO_SUBJECT_TEACHER`** | **その科目を教えられる講師が出勤できない** | 出られる講師はいるが、誰も `TeacherSubject` にその科目を持たない |
| `ALL_AT_LIMIT` | 候補者が全員上限に達している | 候補はいるが H6〜H8 で全員弾かれた |
| `DEMAND_EXCEEDS_SUPPLY` | 候補者数が必要人数に足りない | 候補者数 < 必要人数 |
| `LOCKED_BLOCKED` | ロック済みの割当で埋まっている | ロックが需要枠を占有している |

`NO_SUBJECT_TEACHER` は今回の設計で最も重要な理由コードである。
**「人は足りているのに、その科目が教えられない」という状態を名指しできる**ようにする。
これが見えないと、現場は「人数は合っているのになぜ授業が組めないのか」が分からない。

**段階3：生徒が配置できない理由**

| 理由コード | 表示 | 判定 |
| --- | --- | --- |
| `NO_TEACHER_FOR_SUBJECT` | その科目の担当講師が出勤していない | 段階2の未充足がここに波及した |
| `ROOM_FULL` | ブースが埋まっている | 収容人数の上限 |
| `NO_ROOM_FOR_FORMAT` | その形態に使える教室がない | 集団授業なのに集団教室が空いていない |
| `CONFLICT_PAIR` | 同席させない組み合わせで置けない | `StudentConflict` に該当 |
| `STUDENT_DOUBLE_BOOKED` | 生徒が同じ時間に別の授業に入っている | 受講予定の重複 |

**計画全体に対する警告**

| 警告コード | 表示 |
| --- | --- |
| `NOT_SUBMITTED` | 未提出の講師がいる（氏名と件数を出す） |
| `NG_ASSIGNED` | 「出られない」コマに割当がある（手修正の結果として発生しうる） |
| `CLOSED_ASSIGNED` | 休校日に割当が残っている（休校が後から決まった場合） |
| `UNBALANCED` | 偏り（最大−最小）が閾値以上（既定 4コマ） |
| `BELOW_MIN` | 週の下限コマ数を満たしていない講師がいる |
| **`TIMETABLE_INFEASIBLE`** | **このシフトでは時間割が組めない**（FR-C12 の検証結果。確定前に必ず出す） |
| **`NO_SUBJECT_REGISTERED`** | 担当科目が1件も登録されていない講師がいる |
| **`SUBJECT_SINGLE_POINT`** | ある科目を教えられる講師が1人しかいない（その人が休むと授業が成立しない） |

`SUBJECT_SINGLE_POINT` は割当を止めるものではないが、**運営上のリスクを可視化する**ために出す。
「英語はこの先生しかいない」という状態を数字で見せることで、採用や研修の判断材料にする。

### 7.3.6 講師への出力

確定後、講師側画面（`/t`）の月カレンダーに自分の確定出勤が表示される（既存の表示に接続）。
段階3まで確定していれば、自分が担当する授業と生徒も表示される（既存の `/t/lessons` に接続）。
**確定前の下書きは講師に一切見せない。**

### 7.4.1 ハード制約（違反する解を出してはならない）

自動作成・手修正のどちらでも守る。**画面で押せなくするだけでは不十分で、
サーバー側の書き込み処理でも必ず検証する**（フォームの値は書き換えられるため。
既存 `lib/shifts.ts` が `isClosedDate()` で同じことをしている）。

| ID | 制約 | 違反時の扱い |
| --- | --- | --- |
| H1 | `NG`（出られない）のコマに割り当てない | 保存を拒否 |
| H2 | 未回答のコマに割り当てない | 自動作成では候補にしない。手修正は警告のうえ許可（当日の緊急対応があるため） |
| H3 | 休校日（`SchoolEvent.kind=CLOSED`）に割り当てない | 保存を拒否。**ただし外すことは常に許す**（休校が後から決まった場合の後始末） |
| H4 | 同一講師が同一の 日 × コマ に重複して入らない | `@@unique([teacherId, date, periodId])` で担保（既存） |
| H5 | 1コマの割当人数が必要人数を超えない | 自動作成では発生させない。手修正は警告のうえ許可 |
| H6 | 1日あたりの上限コマ数を超えない | 保存を拒否 |
| H7 | 1週（日曜〜土曜）あたりの上限コマ数を超えない | 保存を拒否 |
| H8 | 連続コマ数の上限を超えない | 保存を拒否 |
| H9 | `active=false` の講師に割り当てない | 保存を拒否 |
| H10 | `locked=true` の割当は自動作成で変更・削除しない | エンジン側で対象外 |
| H11 | 確定済み（`CONFIRMED`）の計画に対して自動作成を実行しない | 実行を拒否。変更するには確定解除が必要 |
| **H12** | **担当できない科目に割り当てない**（`TeacherSubject` にその科目が無い講師を、その科目の需要に充てない） | 保存を拒否 |
| **H13** | **同一講師を、同じ日・同じコマの複数の需要枠に充てない**（同時に2教科は持てない） | 自動作成では発生させない。手修正は拒否 |

**段階3（時間割）のハード制約**

| ID | 制約 | 違反時の扱い |
| --- | --- | --- |
| H14 | 1つの授業枠の講師は、その時間に他の教室にいない | 保存を拒否 |
| H15 | 1つの教室・ブースに、収容人数（`Room.capacity`）を超えて生徒を置かない | 保存を拒否 |
| H16 | 同じ生徒を、同じ日・同じコマの複数の授業に置かない | 保存を拒否 |
| H17 | 授業の形態と教室の形態が一致する（集団授業を個別ブースで開かない） | 保存を拒否 |
| H18 | `StudentConflict` に登録された組み合わせを同じブースに置かない | 保存を拒否 |
| H19 | 授業の担当講師は、その日そのコマに出勤が確定している | 保存を拒否 |

**H12 が今回の設計の要になる。** これが無いと、必要人数だけ合っていて誰も英語を教えられない
シフトが「正常」として確定できてしまう。逆にこれがあることで、
**段階2の出力は「時間割が組める形」であることが機械的に保証される。**

**H2・H5 を「警告のうえ許可」にしている理由** — 全体要件「エラー時でも手動で修正できるようにする」
に従う。自動化が想定しない事態（当日の欠員など）で人が上書きできる余地を残す。
ただし赤い警告として盤面とサマリに残り続ける。

**FR-S7 について** — 生徒の相性・騒音は毎晩の口頭ミーティングで共有される暗黙知であり、

これで暗黙知のすべては拾えないが、事故の大半は防げる。残りは段階3の手修正で対応する。

### 7.5.2 B. 需要の定義

| ID | 要件 | 優先 |
| --- | --- | --- |
| FR-B1 | **生徒の受講予定から、日 × コマ × 科目 × 形態 ごとの必要講師数を自動算出する**（→ 算出式は下記） | 必須 |
| FR-B2 | 算出結果は管理者が上書きできる（模試の監督枠、体験授業の対応枠など） | 必須 |
| FR-B3 | 必要人数 0 のコマは「授業を開かない」扱いとし、盤面でも割当対象から外す | 必須 |
| FR-B4 | 休校日には需要を生成しない | 必須 |
| FR-B5 | **需要（科目別）と、希望の供給（その科目を教えられる講師の延べ出勤可能コマ数）を並べて表示する** | 必須 |
| FR-B6 | 上記を**科目ごとに**表示し、どの科目が足りないかを自動作成の実行前に示す | 必須 |
| FR-B7 | 手入力のみの運用もできる（生徒データが揃っていない導入初期のため） | 必須 |
| FR-B8 | 前回の需要をコピーして作れる | 任意 |

#### 必要講師数の算出式

生徒の受講予定を「日 × コマ × 科目 × 形態」でまとめ、形態ごとの定員で割る。

```
必要講師数(日, コマ, 科目, 形態) = ceil( その枠の生徒数 ÷ 形態ごとの担当上限 )

  形態ごとの担当上限:
    集団（GROUP）     … 集団教室の定員（Room.capacity）
    個別1対1（INDIV_1）… 1
    個別1対2（INDIV_2）… 2
```

例：火曜2限に英語・個別1対2 の生徒が5人 → `ceil(5 ÷ 2) = 3人` の英語講師が必要。

**集団授業は科目ではなく学年・クラスでまとまることが多い**ため、
集団の受講予定は「科目 + クラス名」で束ね、1クラス＝講師1人として数える。
このクラス編成そのものを自動で決めることは本要件に含めない（→ 7.7）。

**FR-B5・B6 の意味** — 「英語は延べ40コマ必要だが、英語を教えられる講師の出勤可能枠は
延べ25コマしかない」ということが、自動作成を回す前に分かる。
自動作成の結果を見て初めて足りないと気づくのでは遅い。**この画面は募集・シフト依頼の判断材料になる。**

| FR-T7 | 時間割は段階2と別に確定できる。確定すると講師の画面に自分の担当授業が出る | 必須 |
| FR-T8 | 確定後の当日変更（欠席・振替・講師交代）に対応できる | 必須 |
| FR-T9 | 同じ生徒が続けて同じ講師になるよう配慮する（担当の継続性） | 任意 |
| FR-T10 | 学年の近い生徒を同じブースにまとめる | 任意 |

**FR-T8 について** — 時間割は確定後も動く。生徒が休めば `Attendance` が `ABSENT` になり、
既存の欠席者カードが自動生成される（試作品で実装済み）。講師が急に休んだ場合の差し替えは、
段階3の手修正で行う。**段階2の確定シフトは動かさない**（給与計算の根拠は勤怠実績側で持つため。
試作品の `ShiftAssignment`＝予定 / `DutyRecord`＝実績 の分離をそのまま活かす）。

### 7.5.4 D. 確認・修正

| ID | 要件 | 優先 |
| --- | --- | --- |

| FR-D5 | **セルをロックできる**（再実行で動かさない）（新規） | 必須 |

### 7.5.5 割当アルゴリズム仕様

**他の技術者が実装しても同じ結果になるよう、処理順・評価式・同点処理まで規定する。**
外部の最適化ソルバーは使わない（依存を増やさず、結果を説明できるようにするため）。

#### 用語

- **スロット** — （**日, コマ, 科目, 形態**）の組。必要人数 `required(s)` を持つ。
  「7/15 の2限に、英語を、個別1対2で、3人」が1スロット
- **候補** — そのスロットに対して次をすべて満たす講師
  1. その日そのコマに `OK` または `PREFER` を出している
  2. **その科目を `TeacherSubject` に持っている**（H12）
  3. その日そのコマにまだ他のスロットへ割り当てられていない（H13）
  4. H1〜H9 に反しない、`active` な講師
- `available(t)` — 対象期間で講師 t が `OK`/`PREFER` と答えたコマ数
- `assigned(t)` — 処理中の時点で t に割り当てたコマ数
- `fillRate(t) = assigned(t) / available(t)`（`available(t)=0` の講師は候補にならない）
- `level(t, 科目)` — `TeacherSubject.level`（1=可 / 2=得意 / 3=専門）

#### フェーズ0：前処理

1. 対象期間の日を列挙し、休校日を除く
2. 各日について `termKindOfDate()` で期タイプを決め、そのコマ一覧を引く
3. `ShiftDemand` を引き、`required > 0` のスロット（日 × コマ × 科目 × 形態）のみを対象にする
4. `mode=FULL` なら、`locked=false` の既存割当を削除する
5. ロック済み割当を `assigned(t)` の初期値に加算し、スロットの残必要人数から差し引く
6. `respectPrevious=true` なら、直前30日間の `fillRate` を `carryOver(t)` として保持する
7. **科目ごとに候補講師を索引化する**（`TeacherSubject` を1回引いてメモリ上に持つ）

#### フェーズ1：貪欲割当

**スロットの処理順**（制約の厳しいものから埋める）:

```
1. 候補者数 昇順          … 選択肢の少ないスロットを先に埋める
2. 残必要人数 降順        … 多く必要なスロットを先に
3. date 昇順
4. period.order 昇順
5. subjectId 昇順         … 同点時の決定打
```

**この順序が科目の希少性を自動的に扱う。** 「理科を教えられるのは2人だけ」という状況では、
理科のスロットの候補者数が少ないため先に処理され、貴重な理科講師が
他の科目に取られる前に確保される。科目のために特別な優先ルールを足す必要はない。

各スロット `s` について、候補者を評価値の降順に並べ、上位から残必要人数ぶんを割り当てる。

**評価式**:

```
score(t, s) =   W_FAIR    × (1 − effectiveFillRate(t))
              + W_SUBJ    × ((level(t, s.科目) − 1) ÷ 2)
              + W_PREFER  × (希望が PREFER なら 1、OK なら 0)
              + W_MINWEEK × (その週の割当が下限未満なら 1、そうでなければ 0)
              + W_CONT    × (同じ日の隣接コマに既に入っていれば 1、いなければ 0)
              − W_LOAD    × (その日の割当コマ数 ÷ その日の上限コマ数)
              − W_SCARCE  × (その講師が担当できる科目の希少度の平均)

effectiveFillRate(t) = respectPrevious ? (fillRate(t) + carryOver(t)) / 2 : fillRate(t)

希少度(科目) = 1 − (その科目を担当できる講師数 ÷ 全講師数)
```

**重みの既定値**（`ShiftPlan.weights` に保存し、画面から変更可）:

| 記号 | 既定値 | 意図 |
| --- | --- | --- |
| `W_FAIR` | 1.00 | 公平性。まだ割当の少ない講師を優先する（主目的） |
| `W_SUBJ` | 0.50 | その科目の専門・得意な講師を優先する（`level` 1→0 / 2→0.25 / 3→0.50） |
| `W_PREFER` | 0.40 | `◎できれば入りたい` を `○出られる` より優先する |
| `W_MINWEEK` | 0.60 | 週の最低コマ数に届いていない講師を優先する（社員・生活給の担保） |
| `W_CONT` | 0.25 | 細切れ出勤を避け、連続したコマにまとめる |
| `W_LOAD` | 0.30 | 同じ日に詰め込みすぎない |
| `W_SCARCE` | 0.35 | **希少な科目を持つ講師を、誰でも教えられる科目に使わない** |

**`W_SCARCE` の意図** — 「理科も英語も教えられる講師」が英語のスロットに先に取られると、
理科が埋まらなくなる。多くの講師が教えられる科目には、汎用的な講師を優先して充てる。
これは公平性（`W_FAIR`）とわずかに衝突するため、重みは控えめにしてある。

**同点処理**（R1：再現性のため必ずこの順で決める）:

```
1. score 降順
2. level(t, s.科目) 降順  … 専門性の高い講師を優先
3. available(t) 昇順      … 出られる日が少ない講師を優先（貴重な候補を使い切らない）
4. teacherId 昇順         … 最終的な決定打。乱数は使わない
```

割り当てたら次を更新する。

- `assigned(t)`、その日・その週のカウンタ、連続コマ数
- H6〜H8 に達した講師は以降のスロットで候補から外す
- **同じ日・同じコマの他のスロットの候補から `t` を外す**（H13。同時に2教科は持てない）

#### フェーズ2：局所改善

フェーズ1の後に残った未充足スロットを、割当の移動で埋められないか探索する。

```
未充足スロット s を（date 昇順, period.order 昇順, subjectId 昇順）に走査:
  s に入れたいが上限で弾かれた講師は対象外
  s の候補 t のうち、他スロット s2 に割当済みの t について:
    s2 を代替できる講師 u（s2 の科目を持ち・制約OK・その日そのコマに未割当）がいるなら
      t を s2 → s へ移し、u を s2 に入れる
    採用条件: 総未充足人数が減る、
              または 同数かつ 偏り spread が小さくなる
  反復上限: スロット数 × 4 回。上限に達したら打ち切る
```

**この入れ替えが科目のねじれを解く。** 「英語も数学もできる A さんが数学に入っていて、
英語のスロットが埋まっていない。数学は B さんでも代われる」という状況で、
A さんを英語へ、B さんを数学へ移す。人が盤面を睨んでやっていた調整がこれにあたる。

走査順を固定するため、探索は常に上記の順序で行い、最初に条件を満たした入れ替えを採用する
（最良を全探索しない。再現性と処理時間を優先する）。

#### フェーズ3：結果の生成

1. 割当を `ShiftAssignment` に保存（`source=AUTO`、`subjectId`、`format`、`score` を含む）
2. 未充足スロットに 7.3.5 の理由コードを付与（`NO_SUBJECT_TEACHER` の判定を含む）
3. 計画全体の警告を判定
4. サマリを `ShiftPlan.lastResult` に保存

#### 計算量と性能目標

スロット数 S（1か月・6コマ・科目5なら最大 930）、講師数 T（想定 ≤ 50）。
科目を入れたことでスロット数は増えるが、**1スロットあたりの候補者数は逆に減る**
（その科目を教えられる講師だけになる）ため、全体の計算量は同程度に収まる。

フェーズ1は `O(S × T log T)`、フェーズ2は反復上限つき。

**目標：1か月ぶん・講師50名・コマ6・科目5で 3秒以内**（→ 7.6 完了条件 AC-11）。

### 7.5.5b 時間割の作成アルゴリズム（段階3）

確定した出勤シフトに生徒を割り当てる。段階2と同じく、決定的な貪欲法で作る。

#### 入力

- 確定した `ShiftAssignment`（講師 × 日 × コマ × 科目 × 形態）
- その日そのコマの `StudentSchedule`（生徒 × 科目 × 形態）
- `Room`（`format` / `capacity`）
- `StudentConflict`（同席させない組み合わせ）

#### 手順

日 × コマ ごとに独立して処理する（日をまたぐ制約が無いため）。

```
各（日, コマ）について:
  1. 出勤が確定している講師を、担当科目つきで列挙する
  2. その枠の受講予定を「科目 × 形態」でまとめる
  3. 集団授業を先に確定する
       … 集団はクラス単位で人数が決まっており、選択の余地が少ない
       … 集団教室（Room.format=GROUP）を割り当てる
  4. 個別授業を処理する:
       生徒を次の順に並べる:
         a. 同席制約(StudentConflict)を持つ生徒 … 置き場所が限られるため先に
         b. 学年 昇順
         c. studentId 昇順
       各生徒を、次の条件を満たす最初のブースに入れる:
         - その科目を担当する講師が付いている
         - 定員に空きがある
         - 既に入っている生徒と StudentConflict が無い
       入るブースが無ければ、空きブースに新しい授業枠を作る
       それも無ければ「未配置」として理由付きで記録する
  5. 作成した授業枠を Lesson、置いた生徒を Attendance として保存する
```

**集団を先に処理する理由** — 集団授業は「このクラスはこの教室でこの人数」と決まっており
動かす余地が少ない。柔軟性の低いものから確定させるのは、段階2でスロットを
候補者数の少ない順に処理するのと同じ考え方である。

**同席制約を持つ生徒を先に置く理由** — 後回しにすると、
置ける場所が全部埋まった後で行き場を失う。

#### 出力

- `Lesson` + `Attendance`
- 未配置の生徒一覧（理由コード付き）
- ブース使用率

#### 性能目標

日 × コマ ごとに独立しているため、1日ぶんは瞬時に終わる。
**1か月ぶん・生徒300名で 5秒以内。**

#### アルゴリズムの選定理由

線形計画・制約充足ソルバーを使えば最適解が得られるが、(a) 依存パッケージが増える、
(b) 「なぜこの人がこのコマなのか」を現場に説明できない、(c) 制約が少し変わると解が大きく飛び、
先月と全く違うシフトが出て混乱する、という問題がある。
本要件は**最適性より説明可能性と安定性を優先**し、貪欲法＋限定的な局所改善とする。

### 7.5.6 E. 確定と共有

| ID | 要件 | 優先 |
| --- | --- | --- |
| FR-E1 | 計画は `DRAFT`（下書き）→ `CONFIRMED`（確定）の状態を持つ | 必須 |
| FR-E2 | 確定は管理者のみが実行できる | 必須 |

### 7.5.7 データモデル

既存（`juku_HR/prisma/schema.prisma`）への追加・変更。
**共通ルール**：日付は `"YYYY-MM-DD"`、時刻は `"HH:MM"` の文字列で持つ（タイムゾーン起因の1日ずれを避けるため）。
SQLite は enum 非対応のため、区分値は `String` + `lib/constants.ts` の定数で表す。

#### 新規モデル

```prisma
  actorId   Int
  /// 確定解除の理由など
  reason    String @default("")

  createdAt DateTime @default(now())

  plan ShiftPlan @relation(fields: [planId], references: [id], onDelete: Cascade)

  @@index([planId, createdAt])
}
```

#### 既存モデルの変更

```prisma
model ShiftAssignment {
  // --- 既存 ---
  id        Int    @id @default(autoincrement())
  teacherId Int
  date      String
  periodId  Int
  termId    Int?
  note      String @default("")

  // --- 追加 ---
  /// どの計画で作られたか。既存データ移行のため null 可。
  planId    Int?
  /// 担当する科目。どの需要を埋めた割当かを表す。
  /// これが無いと「人数は足りているが時間割が組めない」シフトを検出できない。
  /// 既存データ移行のため null 可だが、自動作成では必ず入る。
  subjectId Int?
  /// GROUP | INDIV_1 | INDIV_2。給与のコマ給単価に直結する。
  format    String? 
  /// AUTO(自動作成) | MANUAL(手修正)
  source    String  @default("MANUAL")
  /// true なら再実行しても動かさない
  locked    Boolean @default(false)
  /// 割当時の評価値。「なぜこの人か」の根拠として残す。
  score     Float?

  plan    ShiftPlan? @relation(fields: [planId], references: [id])
  subject Subject?   @relation(fields: [subjectId], references: [id])
  // 既存のリレーションは変更しない
  @@unique([teacherId, date, periodId])
  @@index([date])
  @@index([planId])
}
```

**`@@unique([teacherId, date, periodId])` を維持することが H13 を担保する。**
同じ講師が同じコマで2科目を持てないことが、DB のレベルで保証される。

`ShiftRequest` は変更しない。あわせて、Prisma は逆側のリレーションフィールドを必要とするため
以下を追加する。

| モデル | 追加するフィールド |
| --- | --- |
| `Teacher` | `shiftRule TeacherShiftRule?` |
| `Period` | `demands ShiftDemand[]` / `studentSchedules StudentSchedule[]` / `studentScheduleTemplates StudentScheduleTemplate[]` |
| `Subject` | `demands ShiftDemand[]` / `studentSchedules StudentSchedule[]` / `studentScheduleTemplates StudentScheduleTemplate[]` / `assignments ShiftAssignment[]` |
| `Student` | `schedules StudentSchedule[]` / `scheduleTemplates StudentScheduleTemplate[]` |

**`Lesson` と `Attendance` は変更しない。** 段階3の出力先としてそのまま使える。
これにより、既存の授業記録・出欠管理・欠席者カードが自動作成した時間割の上でそのまま動く。

#### 複数校舎への拡張余地

v1 では校舎を持たないが、将来 `Campus` を足す場合は
`ShiftPlan` / `ShiftDemand` / `Period` に `campusId` を追加し、
複合ユニーク制約に含める形になる。**v1 の実装で校舎を暗黙に前提とした集計を書かない**こと
（例：「全講師」を引くクエリは、後で校舎で絞れるよう関数に切り出しておく）。

| 本番サーバー | **VPS 1台**（年約11,000円） | Vercel は無料プランが商用利用禁止で、選ぶと年85,000円コースになる。定額のVPSなら従量課金の暴発も起きない |

**PostgreSQL への移行は「必要になってから」でよい。** 区分値を `String` で持っているため
移行の負担は小さい（約2〜3人日。移行後も String のままにする。`lib/constants.ts` との二重管理を避けるため）。

**移行が必要になる条件**（規模ではなく構成で決まる）:

- アプリサーバーを2台以上にしたくなったとき（SQLite はファイルなので1台の中でしか共有できない）
- サーバーレス環境に置きたくなったとき
- 同時に書き込む人が数百人規模になったとき

1校舎（講師50・生徒300）なら10年運用しても問題なく、3〜5校舎でも1台に載っていれば足りる。
データ量が理由で移行することはない（10校舎・5年で約2GB。SQLite は数百GBまで扱える）。
詳細は別紙「費用と工数の見積もり」3-2 節。

> **実装時の必須設定** — SQLite は接続時に **WAL モードを有効にする**こと。
> 試作品の `lib/prisma.ts` では設定されていないが、これが無いと書き込み中に読み取りが
> ブロックされ、同時接続の耐性が大きく下がる。
> ```
> PRAGMA journal_mode = WAL;
> PRAGMA busy_timeout = 5000;
> ```
| 認証 | `node:crypto` のみ（scrypt + 署名付き Cookie） | 試作品と同一。**本番前にログイン試行回数制限・初回パスワード変更の強制・HTTPS 強制が必要**（試作品 README に既述） |
| 認可 | `lib/dal.ts` の DAL パターン | `proxy.ts` は Cookie の有無しか見ない。**認可判定を proxy に書かない**（リダイレクトループの原因。試作品 README に既述） |
| 最適化ソルバー | **使わない** | 7.5.5 の選定理由による |
| テスト | `tsx` の検証スクリプト（`npm run verify`） | 既存の `scripts/verify-*.ts` に `verify-shifts-auto.ts` を追加する |

**依存パッケージを増やす場合は PM の承認を得る。** 試作品は意図的に依存を最小化している。
