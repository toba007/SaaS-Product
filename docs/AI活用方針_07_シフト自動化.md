# AI（LLM）の活用方針

シフト自動化に AI を使うかどうか、使うならどこに使うかの整理。

---

## 1. 結論

| | |
| --- | --- |
| **割当を決める処理に LLM を使うか** | **使わない**（理由は第2節） |
| **LLM を使う場所** | **「言葉 → データ」の変換**。特に**生徒の相性・騒音の暗黙知の吸い上げ** |
| ローカル LLM か API か | **API（仮名化して送る）**。ローカルはこの規模だと100倍以上高くつく |
| 費用の目安 | **年1,500円程度** |
| MVP に入れるか | **入れない。** v2 で段階3（時間割）と一緒に入れる |
| 検討中の適用先 | **管理者の要望を設定に翻訳する**／**授業の録音から授業記録を作る**（第8節） |

**設計の原則を1つに決める。**

> **LLM は「言葉 ↔ データ」の変換にだけ使う。割当の決定には使わない。**

この線を引くと、**LLM が失敗しても不正なシフトは絶対に生成されない。**
制約の検証も割当の決定も、従来どおり決定的なプログラムが行うため。

---

## 2. 割当エンジンに LLM を使わない理由

「AI で自動作成」は響きが良いが、この機能に限っては**要件と正面から衝突する。**

### 2-1. 再現性の要件（R1）を満たせない

要件定義で「**同じ入力なら何度実行しても同じ結果**」を必須にしている（AC-09）。
LLM は温度を下げても完全な再現性を保証しない。

そしてこの要件は技術的なこだわりではなく、**業務上の目的から来ている。**
この機能は「シフトを組む人の忖度や贔屓をなくす」ために作っている。
**やり直すたびに違う結果が出るなら、「気に入らない結果が出たら回し直せる」ことになり、
忖度をなくすという主張そのものが崩れる。**

### 2-2. ハード制約を保証できない

H1〜H19（出られない日に入れない、担当できない科目に入れない、上限を超えない…）は
**1件も破ってはいけない。** LLM は「ほぼ守る」ことはできても「必ず守る」ことは保証できない。

これは給与と労務に直結する。「たまに間違える」では済まない。

### 2-3. 説明できなくなる

評価式なら「公平性1.00 + 科目適性0.50 − 負荷0.30 = この人が選ばれた」と内訳を出せる。
LLM に理由を書かせることはできるが、それは**後付けの説明であって、実際の決定過程ではない。**

忖度というブラックボックスをなくすために作った機能が、
**別のブラックボックスに置き換わっては意味がない。**

### 2-4. そもそも LLM が苦手な問題

930スロット × 講師50人の組み合わせ最適化は、LLM が最も不得意とする種類の問題。
貪欲法なら3秒で終わり、しかも最適に近い答えが出る。

### 2-5. 費用と個人情報

呼ぶたびに課金される（貪欲法は0円）。
そして**全講師の希望データを毎回外部に送ることになる。**

## 3. LLM が決定的に効く場所

**逆に、LLM でしか解けない問題がこの機能の中に1つある。**

### 3-1.【最重要】生徒の相性・騒音の暗黙知を拾う

試作品の README にこう書かれている。

> 生徒の相性と騒音を表すモデルはまだ無い。これは毎晩22時ごろの10分程度のミーティングで
> **口頭で共有されている暗黙知**で、**フォームに書かせる形にすると埋まらない**。設計は保留中。

**これは「構造化されていない言葉を、構造化データに変える」問題であり、LLM の本領。**
要件定義では「同席させないペアの登録だけに絞る」と設計したが、
**その登録すら人手では埋まらない**のが現場の実態。

**やること** — ミーティングのメモ（または音声の書き起こし）を投げて、
`StudentConflict`（同席させない組み合わせ）の候補を抽出させる。

```
入力（メモ）:
「田中と佐藤を隣にしたら全然集中してなかった。あと山本は
 個別だと静かだけど集団だと騒ぐ。鈴木は英語だけ極端に苦手」

出力（候補）:
  [同席NG] 生徒003 × 生徒007  理由: 隣席で集中できていない  確信度: 高
  [メモ]   生徒012  集団授業では騒がしくなる傾向
  [メモ]   生徒019  英語が苦手
```

**人が承認したものだけを保存する。** LLM が抽出したものを自動で DB に書き込まない。
画面にチェックボックスで候補を並べ、管理者が選んで確定する。

これなら**メモを貼るだけ**で、フォームを埋める手間がほぼゼロになる。
「思い出したときに1行足す」よりさらに軽い。

### 3-2. 講師のシフト希望の自由記述を読む

`ShiftRequest.note` は**試作品に既にあるが、使われていない**フィールド。
「テスト前は避けたい」「金曜は20時までなら」といった一言が入る想定になっている。

これを LLM に読ませて、**管理者向けの注意点として整理する**（自動で制約にはしない）。

### 3-3. 作成結果を日本語で説明する

評価値の数字は既にある。それを人が読める文章にする。

```
「今週は英語が3コマ埋まりませんでした。英語を担当できる講師は3名ですが、
 うち2名が火曜を『出られない』としています。
 高橋先生に火曜の調整を打診すると2コマ埋まります。」
```

**数字を作るのはプログラム、文章にするのが LLM。** 判断はしない。

### 3-4. 使わない場所（念のため）

| | 理由 |
| --- | --- |
| 誰をどのコマに入れるかの決定 | 第2節 |
| 制約に違反しているかの判定 | 決定的な検証で足りる。LLM を挟む理由が無い |
| 必要人数の算出 | `ceil(生徒数 ÷ 定員)` の割り算。LLM は不要 |
| 生徒の配置（時間割） | 制約充足問題。第2節と同じ理由 |

## 3-5. 実測（2026-08-08・ローカル実行）

推測ではなく、実際に動かして採点した結果（`npm run compare:models`）。

| | |
| --- | --- |
| 環境 | Ollama 0.32.6 / CPU実行（Intel Iris Xe のためGPU不使用） |
| PC | i7-1165G7・4コア・メモリ16GB |
| 費用 | **0円** |

### 採点の設計

現場のメモを模した6項目のテキストに対し、**期待する結果を先に書いてから機械的に採点**した。
各モデル3回ずつ実行し、毎回同じ判定になるかも見る。

**本命は「曖昧なペア」の項目。** 「〜かも」「〜な気がする」という書き方は、
確信が持てないから口頭で共有されているという暗黙知の性質そのものなので、
**現場のメモではこの書き方が多いはず。ここを落とすと機能の価値が半減する。**

### 結果

| 採点項目 | gemma3:4b | **gemma4:e2b-it-qat** |
| --- | --- | --- |
| 明示的なペア（田中×佐藤） | 3/3 | **3/3** |
| **曖昧なペア（田中×鈴木）** | **1/3 ✕** | **3/3 ○** |
| 非該当を除外（山本×伊藤） | 3/3 | **3/3** |
| 個人の特徴（鈴木・騒ぐ） | 3/3 | **3/3** |
| 個人の特徴（高橋・英語） | 3/3 | **3/3** |
| **正解** | **4/5** | **5/5** |
| 平均所要時間 | 31.7秒 | 94.2秒 |
| ライセンス | 独自（制限あり） | **Apache 2.0** |

座席と無関係な項目（「模試の監督が1人要る」）は、両方とも正しく無視した。

### 結論：gemma4:e2b-it-qat を採用する

**曖昧なペアを 3/3 で拾える。** ここが gemma3 との決定的な差で、
事前に「4Bクラスには荷が重い」と見込んでいた部分をクリアした。

**3倍遅い（32秒 → 94秒）が、問題にならない。**
1日1回、ミーティング後にまとめて流す使い方なので、対話的な速さは要らない。

**ライセンスも Apache 2.0** になり、他のライブラリと同じ扱いでよくなった（→ 第5節）。

> **gemma3 の 1/3 という数字に注意。** 「たまに拾える」は「拾えない」より扱いにくい。
> 実行するたびに結果が変わると、現場は結果を信用しなくなる。
> **安定して正解することが、たまに正解することより重要。**

### 副産物：小さいモデルは出力の表記が揺れる

実際に返ってきた仮名IDの形。

```
"生徒003"  "生徒 003"  "生徒003さん"  "００３"  "None"  "生徒005 & 生徒006"
```

完全一致で照合すると**正しく読めているのに全部捨てる**ことになり、
実際に一度「候補ゼロ」になった。数字だけを取り出して照合する処理（`resolveAlias`）で解決。
**API の大きいモデルに切り替えても、この耐性は残しておく。**

### 残っている課題

| | 内容 |
| --- | --- |
| 確信度が全部 low になる | 明白なペアも「△」になる。確信度が情報として機能していない。プロンプトの調整で改善するか要検証 |
| テストデータが1件 | 6項目のメモ1本でしか測っていない。**実際のメモ10本ほどで測り直す**必要がある |
| API と比べていない | ローカルで足りているので急がないが、比較の仕組みは用意済み（`npm run compare:models -- <model>`） |

## 4. ローカル LLM か、API か

### 費用の比較（この規模での実測見込み）

| | 年額 | 備考 |
| --- | --- | --- |
| **API（Claude）** | **約1,500円** | 下の内訳参照 |
| ローカル LLM（GPU付きVPS） | **12万〜36万円** | 月1万〜3万円 |
| ローカル LLM（塾のPCで動かす） | 0円 | ただし**そのPCが止まると機能も止まる** |

**現在の構成（月763円・メモリ1GB のVPS）では、実用的なローカル LLM は動かない。**
動かすには別途 GPU 付きのサーバーが必要で、**サーバー代（年11,000円）を大きく超える。**

### API の費用の内訳

| 用途 | 頻度 | 1回あたり | 年額 |
| --- | --- | --- | --- |
| 同席ペアの抽出（3-1） | 1日1回 × 250日 | 約4円 | 約1,100円 |
| 結果の説明文（3-3） | 月1回 | 約9円 | 約110円 |
| 希望メモの整理（3-2） | 月1回 | 約9円 | 約110円 |
| | | **合計** | **約1,300円** |

※ Claude Opus 5（$5/$25 per 1M tokens）、1ドル150円換算。
より安いモデル（Claude Haiku 4.5：$1/$5）を使えば **5分の1** になる。
どちらを使うかは、実際の抽出精度を見て決める。

### 個人情報の問題と、その解決

**外部 API に生徒の名前や様子を送るのは、個人情報の第三者提供にあたる。**
塾には委託先を監督する義務が生じ、利用目的の明示も必要になる。

**解決策：仮名化してから送る。**

```
[塾HR のDB]                    [送信するデータ]
田中 太郎 (id=3)      →        「生徒003」
佐藤 花子 (id=7)      →        「生徒007」

  ↓ ローカルで置換                    ↓ API へ

「田中と佐藤を隣に…」    →    「生徒003と生徒007を隣に…」

  ↑ ローカルで復元                    ↓ 結果

  田中 × 佐藤 の候補     ←    生徒003 × 生徒007
```

**実名は一切システムの外に出ない。** 対応表はサーバーのメモリ上だけで持ち、保存もしない。
これで「ローカル LLM でないと個人情報が守れない」という理由が消える。

**ただし、仮名化の実装は必ずテストする。** 名前の書き漏らしが1件でもあると意味がなくなるので、
「送信前のデータに実名が含まれていないこと」を検証する処理を入れる（→ 完了条件）。

### 判断

**API + 仮名化を推奨する。**

- 費用が100分の1以下
- 現在のサーバー構成を変えなくてよい
- 仮名化で個人情報の問題は解消できる
- 抽出の精度が高い（暗黙知の読み取りは難しいタスクなので、ここは効く）

ローカル LLM を選ぶ理由は「どうしてもデータを外に出せない」という方針がある場合のみ。
その場合は**サーバー費用が年12万円以上に増える**ことを前提に判断する。

## 5. 実装方針

### 追加する依存パッケージ

| パッケージ | ライセンス | 費用 |
| --- | --- | --- |
| なし（ローカル実行の場合） | — | **0円**。Ollama は `fetch` で呼ぶだけ |
| `@anthropic-ai/sdk`（API に切り替える場合） | MIT | 0円（API利用料は別） |

ローカル実行なら**依存パッケージは1つも増えません**。API に切り替えるときだけ
PM の承認が要ります（→ 別紙「ライブラリのライセンスと費用」#1）。

### モデルのライセンス（ライブラリと同じ確認が要る）

**モデルにもライセンスがある。** ライブラリと同じ基準で確認する。

| | ライセンス | 商用利用 |
| --- | --- | --- |
| **Ollama**（実行環境） | MIT | ○ 無条件 |
| **Gemma 3** | **Gemma Terms of Use（独自）** | △ 許可されるが**制限あり**（下記） |
| **Gemma 4** | **Apache 2.0** | **○ 無条件** |

**Gemma 3 は Apache 2.0 ではない。** 使用禁止ポリシー、下流への引き継ぎ義務
（再配布するなら受け取った人にも同じ制限を課す契約が要る）、Google 側の一方的な終了権が付く。
塾の内部ツールとして使う分には問題ないが、**MIT や Apache のような「無条件」ではない。**

**2026年4月の Gemma 4 で Apache 2.0 に変わった。** Google は独自条項・再配布制限・
商用例外をすべて撤廃したと明言している（[Google Open Source Blog](https://opensource.googleblog.com/2026/03/gemma-4-expanding-the-gemmaverse-with-apache-20.html)）。

**採用するのは Gemma 4。** ライセンスの検討が不要になり、他のライブラリと同じ扱いでよくなる。

> **ルール：モデルを追加・変更するときは、ライブラリと同じようにライセンスを確認する。**
> 「無料でダウンロードできる」ことと「無条件で使える」ことは別。

### 料金が発生する条件

**今の構成（Ollama ローカル + Gemma 4）は永久に0円。** 実行回数の制限もない。
課金が起きるのは次に手を出したときだけ。

| きっかけ | 費用 |
| --- | --- |
| **Ollama Cloud に登録する** | Pro $20/月・Max $100/月。**ローカル実行とは別サービス。混同しやすいので注意** |
| Claude API に切り替える | 1回約4円（→ 第4節） |
| GPU付きサーバーを借りる | 月1万〜3万円 |

### 置き場所

| ファイル | 内容 |
| --- | --- |
| `lib/ai/anonymize.ts` | **仮名化・復元。実名を外に出さないための要。ここを最初にテストする** |
| `lib/ai/extract-conflicts.ts` | メモ → 同席NG候補の抽出（3-1） |
| `lib/ai/explain-result.ts` | 作成結果 → 日本語の説明（3-3） |
| `app/(main)/students/conflicts/import/page.tsx` | メモを貼って候補を確認・承認する画面 |

**割当エンジン（`lib/shifts-auto.ts`）からは AI を一切呼ばない。**
エンジンは Prisma にも AI にも依存しない純粋関数のまま保つ。

### コード例（同席NG候補の抽出）

```ts
import Anthropic from "@anthropic-ai/sdk";
import { anonymize, restore } from "./anonymize";

const client = new Anthropic(); // APIキーは環境変数から（.env は git に入れない）

const SCHEMA = {
  type: "object",
  properties: {
    pairs: {
      type: "array",
      items: {
        type: "object",
        properties: {
          studentA: { type: "string", description: "仮名ID（例: 生徒003）" },
          studentB: { type: "string", description: "仮名ID" },
          reason: { type: "string", description: "根拠になったメモの記述" },
          confidence: { type: "string", enum: ["high", "medium", "low"] },
        },
        required: ["studentA", "studentB", "reason", "confidence"],
        additionalProperties: false,
      },
    },
  },
  required: ["pairs"],
  additionalProperties: false,
} as const;

/**
 * ミーティングのメモから「同席させない組み合わせ」の候補を抽出する。
 *
 * 実名は送らない。anonymize() で仮名IDに置換してから送り、結果を restore() で戻す。
 * 抽出結果はあくまで候補で、保存する前に必ず管理者が承認する。
 */
export async function extractConflicts(note: string, students: Student[]) {
  const { text, table } = anonymize(note, students);

  const response = await client.messages.create({
    model: "claude-opus-5",
    max_tokens: 16000,
    thinking: { type: "adaptive" },
    system:
      "塾のミーティングメモから、同じブースに座らせない方がよい生徒の組み合わせを抽出します。" +
      "メモに書かれていることだけを根拠にし、推測で組み合わせを作らないでください。" +
      "根拠が弱いものは confidence を low にしてください。",
    messages: [{ role: "user", content: text }],
    output_config: { format: { type: "json_schema", schema: SCHEMA } },
  });

  const block = response.content.find((b) => b.type === "text");
  const parsed = JSON.parse(block!.text) as { pairs: ExtractedPair[] };

  return parsed.pairs.map((p) => restore(p, table));
}
```

**要点**

- **`output_config.format` で出力の形を固定する。** 自由な文章を正規表現で切り出すような処理を書かない
- **`anonymize()` を通してからでないと送信できない**構造にする
- **戻り値は「候補」。** そのまま DB に書かず、画面で承認を経る
- APIキーは `.env` に置き、**git に入れない**（→ セキュリティ要件 2-1）

### 失敗したときの動作

**AI が使えなくても、業務は止まらないこと。**

| 状況 | 動作 |
| --- | --- |
| API がエラーを返した | 画面にエラーを出す。**手入力の画面はそのまま使える** |
| 抽出結果がおかしい | 承認画面で人が捨てる。DB には入らない |
| APIキーが未設定 | AI 機能のボタンを出さない。他の機能は正常に動く |

## 6. 完了条件（AI 部分）

| ID | 完了条件 |
| --- | --- |
| AC-AI1 | **送信データに生徒の実名が1件も含まれていないこと**（仮名化のテスト。最重要） |

**AC-AI6 は設計の原則そのもの。** ここが崩れると、再現性（AC-09）も
ハード制約の保証も一緒に崩れる。

## 7. PM に確認すること

| # | 決めること | 論点 |
| --- | --- | --- |
| 1 | **AI を使うこと自体の可否** | 塾に「AIに生徒の情報を扱わせる」ことの説明と同意が要るか |
| 2 | **仮名化で十分とするか** | 実名を送らなければ問題ないという整理でよいか。**塾側にも確認** |
| 3 | 依存パッケージの追加承認 | `@anthropic-ai/sdk`（MIT・無料） |
| 4 | 使うモデル | Opus 5（高精度・年1,300円）か Haiku 4.5（年260円）か。実際の精度を見て決める |
| 5 | 費用の上限 | 使いすぎを防ぐ上限を設けるか（月◯円で止める等） |
| 6 | いつ作るか | **MVP には入れない。** v2 で段階3（時間割）と同時が自然 |

## 8. 検討中の適用先（2026-08-11 追記）

第1節の原則（**言葉 ↔ データ の変換にだけ使う**）に当てはまるものを2つ検討している。
どちらも MVP には入れない。

### 8-1. 管理者の要望を「設定」に翻訳する

**「作りこまずに、LLM に要望を汲ませればよいのでは」という提案への回答。**

同じことを指しているようで、まったく違う2つの案がある。

| | 内容 | 判断 |
| --- | --- | --- |
| A案 | LLM が割当そのものを出力する | **採らない。** 理由は第2節 |
| **B案** | LLM が要望を**重み・制約の値**に翻訳し、**割当は今のエンジンが解く** | **採れる。** 第1節の原則そのもの |

B案なら、**LLM が失敗しても不正なシフトは出ない。** ハード制約の検証も割当の決定も
決定的なプログラムが行い、LLM が触るのは入口の設定値だけだから。

```
管理者「金曜は学生講師を多めに」
  → LLM が重み（W_◯◯）や制約の値に翻訳
  → 貪欲割当が解く（決定的）
  → 「ご要望は W_◯◯=0.6 として反映しました」と表示して確認させる
```

**ただし、これは「先に詰めなくてよい」という意味にはならない。**
翻訳先の項目が無ければ、翻訳のしようがないため。

| | 先に決める必要がある | LLM に任せてよい |
| --- | --- | --- |
| データモデル（コマ・担当科目・必要人数・形態） | ● | |
| ハード制約 H1〜H14 | ● | |
| 誰が何を見られるか | ● | |
| 重みの既定値（公平性と負荷の配分） | | ● |
| 一時的な要望（今月は◯◯先生の負担を減らす） | | ● |

下2つは、**項目ごとに入力欄を作り込むほうが無駄**になる。要望は毎月変わるので、
画面に固定するのが向いていない。

**表現できない要望への態度を決めておくこと。** 語彙が定義されていないと、LLM は
黙って近いものに丸める。**「その要望は反映できません」と答えられる**必要がある。

### 8-2. 授業の録音から授業記録を作る

**「授業記録を書くのが面倒」という要望への案。** 授業を録音し、議事録のように
授業記録の下書きを作る。言葉 → 言葉の変換なので、原則には合っている。

気をつける点が3つある。

| | 内容 |
| --- | --- |
| **仮名化が効かない** | いまは実名を「生徒003」に置き換えてから送る。**音声そのものを送ると名前も声も出ていく。** 書き起こしてから仮名化するか、音声認識をローカルで回すか、方針が要る |
| **保護者に渡る文書になる** | 授業記録は欠席者カードとして家庭に渡る。**下書きのまま配らせない。** 講師が確認してから確定する（同席NG候補と同じ原則） |
| **「面倒」の中身を確かめる** | 書くのが面倒なのか、思い出すのが面倒なのかで作りが変わる。後者なら、録音より板書の写真から要点を出すほうが軽い |

### 8-3. その前にできること ── 要望の自由記述欄

**LLM を入れる前に、要望を溜めるだけの欄を作る。**

- シフト計画ごとに「今回の要望」を日本語で書けるようにする
- LLM は使わない。溜めるだけ
- 工数は半日程度

これが効く理由は2つある。

- **どんな要望が実際に来るのかが分かる。** いま塾に質問し続けているのと同じ情報を、質問せずに集められる
- 溜まったものが、**そのまま 8-1 の「語彙」の設計材料と、精度を測るテストデータになる**

## 付録：なぜ「AIでシフトを作る」ではないのか（説明用）

社外や塾に説明するときの言い方。

> シフトの割当そのものは、**AIではなく決められた計算式**で行っています。
> これは意図的な選択です。
>
> シフトは給与に直結し、「出られないと答えた日に入れられていた」ようなことが
> 1件でも起きてはいけません。また、この機能はもともと
> 「シフトを組む人の忖度をなくす」ために作っているので、
> **同じ条件なら必ず同じ結果が出ること**と、
> **なぜその人が選ばれたかを数字で説明できること**が必要でした。
>
> AI は別の場所で使っています。
> **毎晩のミーティングで口頭で共有されている「あの2人は隣にしない方がいい」といった
> 経験を、メモから拾い上げてデータにする**ところです。
> ここは今まで誰の頭の中にもあって、どこにも記録されていなかった部分です。
