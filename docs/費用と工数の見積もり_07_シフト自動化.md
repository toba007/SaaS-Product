## 2. 開発中は0円で完結する

試作品（`juku_HR`）は**外部サービスを一切使わない構成**になっている。

| 項目 | 費用 | 理由 |
| --- | --- | --- |
| 開発環境 | 0円 | 自分のPCで動く。`npm run dev` だけ |
| データベース | 0円 | SQLite。ファイル1つ。サーバー不要 |
| ログイン機能 | 0円 | Node.js 標準機能（`node:crypto`）で自作済み。Auth0 等の外部サービスを使っていない |
| 最適化エンジン | 0円 | 商用ソルバーを使わず、自前の貪欲法で書く（要件定義 7.5.5） |
| ライブラリ | 0円 | すべて無料のオープンソース |
| AI・外部API | 0円 | **使っていない。使う予定もない** |

**依存パッケージを増やすときは必ず確認する。** 試作品は意図的に依存を最小化してある。
無料に見えるサービスでも、無料枠を超えると従量課金になるものが多い。

## 3. 本番運用の費用 — ここが分岐点

同じアプリでも、**どこに置くかで年間の費用が8倍違う。**

### 案A：VPS 1台にまとめる（推奨）

サーバーを1台借りて、アプリもデータベースも同じ場所に置く。

| 項目 | 月額 | 年額 |
| --- | --- | --- |
| VPS（[ConoHa VPS 1GB](https://vps.conoha.jp/) 等・2コア/1GB/SSD100GB） | 約763円 | 約9,200円 |
| 独自ドメイン（.com） | 約130円 | 約1,500円 |
| SSL証明書（Let's Encrypt） | 0円 | 0円 |
| データベース | **0円** | **0円** |
| **合計** | **約900円** | **約11,000円** |

**データベースが0円になるのは、SQLite のまま使うから。**
塾1校の規模（講師50名・生徒300名）なら SQLite で十分足りる。
同じサーバーの中のファイルなので、別途サービスを借りる必要がない。

### 案B：Vercel + マネージドDB（避けたい）

| 項目 | 月額 | 年額 |
| --- | --- | --- |
| Vercel Pro（$20/人/月） | 約3,000円 | 約36,000円 |
| マネージドPostgreSQL（Supabase Pro 等） | 約4,000円 | 約48,000円 |
| 独自ドメイン | 約130円 | 約1,500円 |
| **合計** | **約7,000円** | **約85,000円** |

**これが「あとで10万」の正体。** しかも人数課金なので、チームが増えるとさらに上がる。

### 案C：無料で始める（本番では使えない）

| サービス | 無料か | 本番で使えるか |
| --- | --- | --- |
| Vercel Hobby | 無料 | **✕ 商用利用が禁止されている** |
| Supabase Free | 無料 | ✕ 一定期間アクセスが無いとデータベースが一時停止する |
| Cloudflare Pages | 無料・商用OK | △ Next.js の一部機能に制約あり。検証は必要 |

**Vercel の無料プラン（Hobby）は個人の非商用プロジェクト限定で、商用利用は禁止されている。**
判定は「サイトの規模や売上」ではなく「**作った人が報酬を受け取っているか**」で行われる
（[Vercel料金ガイド](https://www.issoh.co.jp/tech/details/8792/) /
[商用利用の判断基準](https://engineer-notes.net/articles/is-vercel-hobby-ok-for-commercial-use)）。

塾が業務で使う時点で商用にあたるため、**無料のまま本番運用することはできない。**
デモや学内発表までなら無料枠で十分。

### なぜ案Aを勧めるか

| | 案A（VPS） | 案B（Vercel） |
| --- | --- | --- |
| 年額 | 約11,000円 | 約85,000円 |
| 人数が増えたとき | 変わらない | 1人あたり年36,000円ずつ増える |
| アクセス急増時の請求 | 定額なので上限が読める | 従量課金。想定外の請求が起きうる |
| データベースの追加費用 | 不要（SQLite） | 必須 |
| 手間 | サーバーの設定・更新を自分でやる | ほぼ自動 |

**案Aの唯一の欠点は手間。** サーバーのOS更新やバックアップを自分で行う必要がある。
ただし塾1校の規模ならアクセスは多くないので、運用の負担も小さい。

> **要件定義の記述を訂正する**
> 要件定義 7.5.10 に「本番DBは PostgreSQL を想定」と書いたが、これは**費用面で不利な選択**だった。
> **SQLite のまま案Aで運用することを推奨に変える。**
> PostgreSQL が必要になるのは、複数校舎に広げて同時アクセスが増えたときで、
> そのときに移行すればよい（区分値を `String` で持っているので移行は難しくない）。

## 3-2. SQLite はどの規模まで持つのか

「複数校舎になったら PostgreSQL」と書いたが、その境目を具体的にしておく。

### 結論

| 規模 | SQLite で足りるか |
| --- | --- |
| 1校舎（講師50・生徒300） | **余裕。10年運用しても問題ない** |
| 3〜5校舎（講師250・生徒1,500） | **足りる。** ただし1台のサーバーに載っていること |
| 10校舎（講師500・生徒3,000） | 動くが、シフト提出の締切日に遅くなる可能性がある |
| それ以上、またはサーバーを2台にしたい | **PostgreSQL へ移行** |

**判断の軸は「校舎数」ではなく、次の3つ。**

### 軸1：データ量 — ここでは絶対に詰まらない

1校舎あたりの年間データ量を数えると、こうなる。

| テーブル | 年間の行数（1校舎） |
| --- | --- |
| シフト希望 | 約75,000 |
| 確定シフト | 約37,500 |
| 生徒の受講予定 | 約30,000 |
| 出欠 | 約30,000 |
| 授業 | 約15,000 |
| 勤怠（打刻・コマ実績） | 約50,000 |
| **合計** | **約24万行 ≒ 40MB / 年** |

10校舎・5年運用でも**約2GB**。SQLite は数百GBまで扱えるので、**データ量が理由で移行することはない。**

### 軸2：同時書き込み — ここが唯一の性能上の限界

SQLite は**同時に書き込める人が1人だけ**という制約がある（読み取りは何人でも同時にできる）。
1回の書き込みは1ミリ秒程度なので、**毎秒数百件までは順番待ちが体感されない。**

このアプリで書き込みが集中するのは**シフト提出の締切日**だけ。

| 場面 | 発生する書き込み |
| --- | --- |
| カレンダーを1マス押す | 1件 |
| 曜日をまとめて入力 | 約25件（その月の該当曜日ぶん） |
| 打刻 | 1件 |
| **自動作成の実行** | **数千件（ただし管理者1人が月1回）** |

**最悪のケース：50人の講師が同じ瞬間に一括入力を押す**
→ 1,250件の書き込み → **約6秒で処理し終わる。**1人あたりの待ちは数秒で、許容範囲。

これが500人（10校舎ぶん）になると1分近くかかる。ここが実質的な上限。

> **注意点：自動作成は長い書き込みになる**
> 自動作成は数千行をまとめて書くため、その数秒間は他の人の書き込みが待たされる。
> 1校舎なら問題ないが、**複数校舎で別々の管理者が同時に自動作成を回すと衝突する。**
> 要件定義でエンジンを「計算はメモリ上、書き込みは最後にまとめて」という形にしているので、
> ロックされる時間は最小限になる（→ 要件定義 7.5.9）。

### 軸3：サーバー構成 — これが本当の分岐点

**SQLite はファイルなので、アプリと同じサーバーの中にしか置けない。**
つまり次の場合は、規模に関係なく PostgreSQL が必要になる。

| こうしたくなったら | 理由 |
| --- | --- |
| アプリサーバーを2台以上にする | 2台から同じファイルを触れない |
| Vercel などのサーバーレスに置く | ファイルが保存され続けない |
| 止めずにバックアップ・自動で切り替える | SQLite では手作業になる |

**校舎が増えても、1台のサーバーで足りるうちは SQLite のままでよい。**

### 移行を考え始める合図

数字を測るより、次の症状が出たら検討する、という運用が現実的。

- サーバーのログに「データベースが使用中（SQLITE_BUSY）」が出始めた
- シフト提出の締切日に、画面の反応が目に見えて遅い
- サーバーの負荷が高く、1台では足りなくなった

### 移行の手間

**約2〜3人日。** 区分値を `String` で持っていて PostgreSQL 固有の機能を使っていないため、
接続設定の変更とデータの移し替えで済む。**先に PostgreSQL にしておく必要はない。**

### 今すぐやっておくべきこと（0円・30分）

試作品の `lib/prisma.ts` を確認したところ、**SQLite の WAL モードが有効になっていない。**
WAL を有効にすると「書き込み中でも読み取りができる」ようになり、同時接続の耐性が大きく変わる。

```
接続時に PRAGMA journal_mode = WAL;
        PRAGMA busy_timeout = 5000;
```

**これは実装段階で必ず入れる。**（→ 要件定義 7.5.10 に追記済み）
上に書いた「毎秒数百件」「50人で6秒」という数字は、WAL が有効な前提のもの。

## 4. 後から出てくる費用（先に潰しておく）

「あとで10万」を防ぐために、**課金が発生しうるものを全部並べておく。**

| 項目 | いつ発生するか | 金額の目安 | 回避策 |
| --- | --- | --- | --- |
| **Vercel の商用利用** | 塾が業務で使い始めた時点 | 年36,000円〜 | **案Aを選べば発生しない** |
| **マネージドDB** | Vercel を選ぶと必須になる | 年48,000円〜 | 同上 |
| **LINE通知** | 講師への通知を LINE でやる場合 | 無料枠を超えると従量課金 | アプリ内通知だけにすれば0円 |
| **メール送信** | パスワード再発行をメールでやる場合 | 無料枠あり。超えると従量 | 管理者が手渡しで再発行すれば0円（試作品は既にこの方式） |
| ドメイン更新料 | 2年目以降 | 業者によって初年度より上がる | 更新料の安い業者を選ぶ |
| バックアップ保管 | 運用開始時 | 数百円/月 or 0円 | VPSの容量内に置けば0円 |
| 従量課金の暴発 | アクセス急増・攻撃を受けたとき | **上限なし** | **定額のVPSなら構造的に起きない** |

**いちばん危険なのは最後の行。** 従量課金のサービスは、攻撃を受けたり設定を誤ったりすると
請求が青天井になる。定額のVPSを選ぶと、この事故が構造的に起こらない。

### 通知手段は0円で始められる

要件定義では「講師への通知」を必須にしているが、**試作品の `Message` 機能（アプリ内通知）を使えば0円。**
LINE やメールは「あると便利」であって、無くても業務は回る。
必要になってから足せばよい（→ 要件定義 7.7）。

### 期間の目安

| 体制 | v1（40人日） | 全部（73人日） |
| --- | --- | --- |
| 2人・フルタイム | 約1か月 | 約1.8か月 |
| 2人・週20時間 | 約2か月 | 約3.6か月 |

**「動くものが見えない期間が2〜3週間続く」ことを、あらかじめ関係者に伝えておく。**

### 削るならどこか

| 削る対象 | 浮く人日 | 影響 |
| --- | --- | --- |

| 変更履歴 | 3人日 | 全体要件に反するので非推奨 |
| 代理入力・締切機能 | 3人日 | 運用でカバーできる |

## 7. 費用以外に確認が必要なこと

金額はかからないが、**後から問題になるもの。**

| 項目 | 内容 |
| --- | --- |
| **個人情報の管理責任** | 生徒・保護者・講師の情報を預かる。事故が起きたときの責任の所在を、開発前に文書で決めておく |
| **バックアップ** | VPSの容量内に置けば0円だが、**やること自体は必須**。DBファイルを1日1回別の場所へ複製する |
| **本番前のセキュリティ対応** | 試作品のログイン機能には、試行回数の制限・初回パスワード変更の強制・HTTPS強制が入っていない（試作品 README に既述）。**費用は0円だが工数が3人日かかる** |
| **運用の引き継ぎ** | 学生チームの場合、卒業後に誰が面倒を見るかを決めておく |
