# セキュリティ要件と、試作品の現状評価

試作品 `juku_HR` / `juku-app` の実際のコードを読んで確認した結果と、本番前に必要な対応。

**扱うデータの性質** — 生徒（未成年）・保護者・講師の個人情報を預かる。
成績や配慮事項を含む場合はさらに慎重な扱いが要る。
**万一漏えいすると、塾の信用に直接かかわる。**

## 2. 見つかった問題

実際にコードを読んで確認したもの。**優先度の高い順**に並べる。

### 2-1.【最優先】データベースファイルが git に入っている

**`juku-app/data/data.json` が git の管理下にある。**

現在は動作確認用のダミーデータなので実害はない。
しかし**このまま実データを入力してコミットすると、生徒・保護者の個人情報が
git の履歴に永久に残る。** git の履歴は後から消すのが非常に困難で、
一度 GitHub に上げてしまうと取り返しがつかない。

| | |
| --- | --- |
| 対応 | `.gitignore` に追加し、`git rm --cached` で追跡から外す |
| 工数 | 0.5人日 |
| **いつまでに** | **実データを入れる前。今すぐでもよい** |

> `juku_HR` 側は正しく設定されている。`.gitignore` に `/dev.db` があり、
> `.env`（`SESSION_SECRET` が入るファイル）も `.env*` で除外されている。
> **`.env` が git に入っていないことは確認済み。** ここは問題ない。

### 2-2.【高】依存パッケージに既知の脆弱性がある

`npm audit` の結果：

| 深刻度 | 件数 |
| --- | --- |
| high | **6** |
| moderate | 5 |
| **合計** | **11** |

Next.js 16.2.10 に対して複数の勧告が出ている（Server Actions の DoS、
SSRF、キャッシュの取り違えなど）。`npm audit fix` で修正できるものが大半。

| | |
| --- | --- |
| 対応 | `npm audit fix` の実行と Next.js の更新。**以後は月1回の定例作業にする** |
| 工数 | 0.5人日（初回）＋ 月0.25人日 |

### 2-3.【高】ログインの試行回数に制限がない

`app/login/actions.ts` に回数制限が無いため、**パスワードの総当たり攻撃ができる。**
試作品 README でも未対応と明記されている。

| | |
| --- | --- |
| 対応 | 同一IDまたは同一IPからの失敗が一定回数を超えたら、一定時間ロックする |
| 工数 | 1人日 |

### 2-4.【中】ログインの応答時間からIDの存在が分かる

`app/login/actions.ts:29-32`

```ts
const ok =
  teacher !== null &&
  teacher.active &&
  verifyPassword(password, teacher.passwordHash);
```

コードのコメントには「**処理時間も変えない**」と書かれているが、**実際には変わっている。**
`teacher` が `null` のとき、`&&` の短絡評価によって `verifyPassword` が実行されない。
`verifyPassword` は scrypt（意図的に重い処理）なので、

- 存在しないID → 数ミリ秒で応答
- 存在するID（パスワード誤り） → 100ミリ秒程度で応答

この差から「**このIDは存在する**」と判別できてしまう。
メッセージを統一した意図が、実装で崩れている。

| | |
| --- | --- |
| 対応 | `teacher` が `null` のときもダミーのハッシュに対して `verifyPassword` を実行する |
| 工数 | 0.5人日 |

### 2-5.【中】打刻用トークンが暗号的な乱数ではない

`prisma/schema.prisma` の `Teacher.punchToken` が `@default(cuid())` になっている。

`/p/[token]` は**ログイン不要**で開ける打刻ページであり、このトークンだけが防御になっている。
cuid は「重複しないID」を作るためのもので、**推測されにくさを保証する設計ではない。**
推測されると他人になりすまして打刻でき、**給与計算の根拠が狂う。**

| | |
| --- | --- |
| 対応 | `randomBytes(32)` による暗号的乱数に変更する。既存トークンは再発行する |
| 工数 | 0.5人日 |

### 2-6.【中】ログアウトしてもセッションを無効化できない

`lib/auth.ts` のセッションは「講師ID + 期限 + 署名」を Cookie に入れた自己完結型で、
**サーバー側に記録が無い。** そのため次の問題がある。

- **ログアウトは手元の Cookie を消すだけ。** 事前に値をコピーされていれば、そのまま使える
- **パスワードを変更しても、既存のセッションは生き続ける**
- 有効期限が**30日**と長い

**部分的な救い** — `lib/dal.ts` が毎回 `teacher.active` を確認しているので、
**講師を「退職」にすればセッションは即座に無効になる。** 最悪の事態は防げる作りになっている。

| | |
| --- | --- |
| 対応 | `Teacher` に版番号を持たせ、Cookie に含める。パスワード変更時に版を上げる。有効期限を短くする（7〜14日） |
| 工数 | 1人日 |

### 2-7.【低】パスワードのハッシュ強度が現行の推奨より低い

`lib/auth.ts:30` の `scryptSync(password, salt, 64)` は Node.js の既定値
（N=16384）を使っている。**現在の推奨（N=131072）より低い。**

平文を保存せず、ソルトを1件ごとに変え、`timingSafeEqual` で比較している点は正しく、
**根本的に危険な作りではない。** 強度を上げるだけの改善。

| | |
| --- | --- |
| 対応 | パラメータを引き上げる。既存パスワードは次回ログイン時に再ハッシュする |
| 工数 | 0.5人日 |

## 3. できていること（評価できる点）

**直す必要がないもの。** 実装時に壊さないよう、理由とともに残しておく。

| | 内容 |
| --- | --- |
| **平文パスワードを保存していない** | scrypt + 1件ごとのソルト。比較は `timingSafeEqual` で時間差を出さない |
| **IDの存在を漏らさない設計思想** | メッセージを統一している（ただし 2-4 の実装漏れあり） |
| **オープンリダイレクト対策** | `login/actions.ts:42` で `next` が `/` 始まりかつ `//` でないことを検証。`//evil.com` を弾く |
| **Cookie の設定が適切** | `httpOnly`（JSから読めない）/ `sameSite: lax` / 本番のみ `secure` |
| **Cookie の改ざんができない** | HMAC-SHA256 で署名。講師IDを書き換えても通らない |
| **認可をDALに一本化** | `lib/dal.ts` で毎回DBを引いて判定。**退職者のセッションが即座に無効になる** |
| **認可を proxy に書いていない** | proxy は Cookie の有無しか見ない。防御を proxy に頼らない判断は正しい |
| **フォームの `teacherId` を信用しない** | 講師側の操作は必ずセッションから引き直す。開発者ツールで値を書き換えても他人のデータに触れない |
| **認可のテストがある** | `scripts/verify-teacher-access.ts` で、講師が他人のデータに触れないことを検証している |
| **打刻トークンの権限が最小** | `/p/[token]` でできるのは打刻だけ。給与明細などは見られない |
| **`.env` が git に入っていない** | `SESSION_SECRET` が漏れていない（確認済み） |
| **デモ用パスワードの流出確認** | `npm run check:password` で既知の流出パスワードでないことを確認する仕組みがある |

`juku-app` 側にも、監査ログ・CSP・リクエストサイズ制限・静的配信のパス制限が実装されている。

## 5. 個人情報保護法の観点

塾は個人情報取扱事業者にあたり、**安全管理措置を講じる義務がある。**
技術的な対策だけでなく、組織としての取り決めが必要になる。

### 開発チームで対応すること（技術的安全管理措置）

上の第4節がこれにあたる。アクセス制御・記録・暗号化（HTTPS）・バックアップ。

### 塾と決めておくこと（開発では解決しない）

| 項目 | 内容 |
| --- | --- |
| **誰がデータの管理責任者か** | 塾か、開発チームか。**文書で明確にする** |
| **利用目的の明示** | 何のために生徒・保護者の情報を集めるかを通知・公表する |
| **未成年の情報の扱い** | 生徒は未成年。保護者の同意をどう取るか |
| **開発チームの立場** | 委託先にあたる場合、塾には**委託先を監督する義務**がある |
| **漏えい時の対応** | 一定の要件を満たす漏えいは、**個人情報保護委員会への報告と本人への通知が義務**。誰が・何日以内に・どう動くかを事前に決める |
| **保存期間** | 卒業・退職した人のデータをいつ消すか |
| **開発中のデータ** | **開発・テストに実データを使わない。** ダミーデータで行う（試作品は既にそうなっている） |

**法令の適用範囲や必要な手続きは、塾の状況によって変わる。**
本番運用の前に、塾の側で確認してもらうこと。開発チームだけで判断しない。

## 6. 運用面

技術的に正しくても、運用で崩れることが多い。

| 項目 | 内容 |
| --- | --- |
| **バックアップ** | DBファイルを1日1回、別の場所へ複製する。**復元の練習を1回やっておく**（取れているが戻せない、が一番多い失敗） |
| **サーバーの更新** | VPSを選ぶとOS更新は自分の責任。月1回の定例作業にする |
| **パスワードの配り方** | 初期パスワードをチャットで送らない。初回変更を強制する（第4節#5） |
| **退職者の処理** | 講師を「退職」にするとセッションが無効になる作りになっている。**退職時に必ず実施するルールにする** |
| **卒業後の運用** | 学生チームの場合、誰が引き継ぐか。**引き継げないなら本番運用を始めない** |
| **アクセス権の見直し** | 誰が管理者権限を持つかを定期的に確認する |

## 7. 要件定義への追加（完了条件）

第7章の完了条件に、次を追加する。

| ID | 完了条件 |
| --- | --- |
| AC-S1 | 講師が他の講師の希望・確定シフト・給与を取得できないこと（既存 `verify-teacher-access.ts` を拡張） |
| AC-S2 | **生徒の受講予定・同席制約に、講師がアクセスできないこと**（今回追加するデータ。管理者のみ） |
| AC-S3 | ログイン失敗が一定回数を超えるとロックされること |
| AC-S4 | 存在しないIDと存在するIDで、ログインの応答時間に有意な差が無いこと |
| AC-S5 | 退職扱いにした講師のセッションが、即座に無効になること |
| AC-S6 | パスワード変更後、変更前のセッションが無効になること |
| AC-S7 | `npm audit` に high 以上の脆弱性が残っていないこと |
| AC-S8 | 個人情報を含むファイルが git の追跡対象に含まれていないこと |
| AC-S9 | 本番環境で HTTP アクセスが HTTPS にリダイレクトされること |

**AC-S2 は今回の要件で新しく増えたリスク。**
生徒の受講予定と「同席させない組み合わせ」は、
**講師には見せるべきでない情報**（特に同席制約は理由が繊細）。
段階3の時間割で講師が見るのは「自分が担当する生徒」だけに限る。
