# MVP：これだけは外せない機能

要件定義（第7章）のうち、**最初のリリースに必ず入れるもの**を切り出したもの。

---

## 1. MVP の判断基準

機能の重要度を議論すると意見が割れるので、**基準を1つに決める。**

> **これが無いと、現場が今までのやり方（手作業）に戻ってしまうか？**

戻ってしまうものは MVP に入れる。戻らないものは後回しにする。
「あると便利」「将来必要」は判断基準にしない。

| | |
| --- | --- |
| **MVP の工数** | **約38人日**（セキュリティの必須対応3.5人日を含む） |
| 全機能との比較 | 83人日 → **38人日（46%）** |
| 期間の目安（2人・週10時間ずつ） | **約4か月** |

---

## 2. MVP に入れるもの

### A. 登録できる（これが無いと自動作成が動かない）

| # | 機能 | 無いとどうなるか |
| --- | --- | --- |
| A-1 | 講師が ◎○× でシフト希望を出せる（曜日一括を含む） | 希望が集まらない。**試作品に実装済み** |
| A-2 | **講師の担当科目を登録できる** | 誰が何を教えられるか分からず、割当が決まらない |
| A-3 | **科目別の必要人数を登録できる**（手入力でよい） | 「何人埋めれば完成か」が無く、自動化が成立しない |
| A-4 | 講師ごとの勤務上限を登録できる | 1人に詰め込む結果が出る |
| A-5 | 休校日を登録できる | 休みの日に人が入る。**試作品に実装済み** |

**A-3 は手入力でよい。** 生徒の受講予定から自動算出する機能（段階1）は MVP に入れない。
最初の1か月は管理者が「火曜2限は英語2人・数学1人」と手で入れる。
それでも今の手作業より速く、**自動作成は問題なく動く。**

### B. 自動で作れる

| # | 機能 | 無いとどうなるか |
| --- | --- | --- |
| B-1 | **ボタン1つで出勤シフトを自動作成できる**（段階2） | この機能の存在意義が無い |
| B-2 | ハード制約 H1〜H13 をサーバー側で検証する | 「出られない日に入っている」シフトが出て、信用されなくなる |
| B-3 | 同じ入力なら同じ結果になる | 「やり直せば有利になる」と疑われ、公平性の主張が崩れる |
| B-4 | 条件が足りなければ理由を出して止まる | なぜ動かないか分からず、問い合わせが増える |

### C. 確認して直せる

| # | 機能 | 無いとどうなるか |
| --- | --- | --- |
| C-1 | 盤面で結果を確認できる | 出来上がりが見えない。**試作品に実装済み** |
| C-2 | **科目別の充足状況が出る**（「英 2/3」） | どこが足りないか分からない |
| C-3 | クリックで手直しできる | 自動作成が外した事情に対応できず、使い物にならない |
| C-4 | **気に入った割当を固定できる** | やり直すたびに手直しが消え、再実行できない |
| C-5 | 講師ごとの担当数・充足率・偏りが出る | 「偏りをなくす」という目的が確認できない |
| C-6 | 埋まらないコマに理由が付く | 「なぜ埋まらないのか」が分からず、対処できない |

**C-4 は見落とされやすいが必須。** 固定できないと「手直し → 再実行 → 手直しが消える」となり、
**実質的に1回しか自動作成を回せない。**

### D. 確定して共有できる

| # | 機能 | 無いとどうなるか |
| --- | --- | --- |
| D-1 | 下書きと確定を区別できる | 検討中のものが講師に見えてしまう |
| D-2 | **確定前の内容は講師に見せない** | 確定していない予定で講師が動いてしまう |
| D-3 | 確定すると講師の画面に自分の出勤が出る | 結局チャットで送ることになり、今と変わらない |
| D-4 | 確定できるのは管理者だけ | 講師が自分のシフトを勝手に確定できてしまう |

### E. 安全に使える（セキュリティの必須分）

| # | 対応 | 工数 |
| --- | --- | --- |
| E-1 | **データベースファイルを git から外す** | 0.5 |
| E-2 | 依存パッケージの脆弱性を修正する（`npm audit fix`） | 0.5 |
| E-3 | HTTPS を強制する | 0.5 |
| E-4 | ログイン試行回数を制限する | 1.0 |
| E-5 | 初回ログイン時のパスワード変更を強制する | 1.0 |

**この5つは「後で」にできない。** 実データを入れた瞬間から必要になる。

## 3. MVP に入れないもの

**入れない理由を明記する。** 「忘れていた」と「意図的に外した」を区別するため。

| 機能 | 入れない理由 | いつ入れるか |
| --- | --- | --- |
| **生徒の受講予定からの需要自動算出**（段階1） | 手入力で代替できる。生徒データの入手元も未確定（→ 要件定義 7.7 #1） | v1.1 |
| **時間割の自動作成**（段階3） | 従来どおり手作業でも業務は回る。ここを外しても**シフト自動化の価値は失われない** | v2 |
| 同席させない組み合わせの登録 | 段階3とセット。段階3が無いと使い道が無い | v2 |
| 提出締切・締切後のロック | 運用（「◯日までに出して」と伝える）でカバーできる | v1.1 |
| 提出状況の一覧・代理入力 | 管理者が盤面を見れば未提出は分かる | v1.1 |
| 変更履歴（`ShiftChangeLog`） | **全体要件には含まれるが**、MVP では監査ログ（誰が何を見たか）を優先 | v1.1 |
| 確定時の通知 | 既存の連絡機能を手動で使えばよい | v1.1 |
| 前月の偏りを引き継ぐ（`respectPrevious`） | 1か月目には過去データが無い | v1.1 |
| 局所改善（アルゴリズムのフェーズ2） | 貪欲割当だけでも実用になる。**手直しで補える** | v1.1 |
| 印刷・CSV出力 | 画面で見られれば足りる | 任意 |
| 複数校舎 | 1校舎で運用してから | 未定 |

**局所改善を外す判断について** — アルゴリズムのフェーズ2（講師の入れ替え探索）は
「英数できるAさんを英語へ、数学はBさんへ」という調整を自動でやる部分。
これが無いと未充足がやや増えるが、**盤面の手直しで人が同じことをできる。**
MVP では貪欲割当（フェーズ1）だけを実装し、実データで効果を測ってから追加する。

## 5. MVP の完了条件

**これが全部通ったらリリースしてよい。**

### 絶対に守れているか

- 「出られない」「未回答」「休校日」への割当が **すべて0件**
- **担当できない科目に割り当てられた講師が0人**
- 1日・週・連続の上限を超えた講師が0人
- 固定した割当が、やり直しても残っている

### 使えるか

- **同じ条件で10回実行して、10回とも同じ結果**
- 講師どうしの担当コマ数の差が **2コマ以内**
- 講師50人・1か月ぶんで **3秒以内**
- 埋まらないコマに **正しい理由が付く**（特に「その科目を教えられる人がいない」）

### 業務が回るか

- 担当科目の登録 → 必要人数の入力 → 希望提出 → 自動作成 → 手直し → 確定 が**通しで完了する**
- **確定前のシフトが講師の画面に一切出ていない**
- 確定後、講師の画面に自分の出勤が出ている
- **自動作成を1回も使わず、手だけでもシフトを完成できる**

### 安全か

- 個人情報を含むファイルが git に入っていない
- `npm audit` に high 以上の脆弱性が無い
- HTTP でアクセスすると HTTPS に飛ぶ
- ログイン失敗が続くとロックされる
- 講師が他の講師の希望を見られない

## 6. リリース後の順番

MVP を出した後、**現場の反応を見てから**次を決める。先に全部決めない。

| 優先 | 内容 | 判断の根拠にすること |
| --- | --- | --- |
| 1 | 提出締切・提出状況の一覧 | 「未提出の督促が面倒」という声が出たら |
| 2 | 局所改善（アルゴリズム） | 未充足が実際に多ければ |
| 3 | 生徒の受講予定 → 需要の自動算出 | 必要人数の手入力が負担になっていれば |
| 4 | 変更履歴・通知 | 運用が固まってきたら |
| 5 | 時間割の自動作成 | ここまで安定してから着手する |

**MVP を出す目的は「現場に使ってもらって、次に何が要るかを知ること」。**
仮置きしている項目（勤務上限の数字・公平性の定義・重みの既定値）は、
**実際に使ってもらわないと正解が分からない。**
